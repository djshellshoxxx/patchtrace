## Finding details

### CORE-1 (Medium): context evidence with a trailing blank line never validates

- File: `src/patchtrace/evidence.py:106-113` builds the evidence text, and `src/patchtrace/interpretation.py:110` checks it.
- Evidence: `build_context` takes `lines = code.splitlines()` and sets `text = '\n'.join(lines[:count])`. For code `...}\n\n`, `splitlines()` returns a trailing `''`, so `text` ends in `\n` and `text.splitlines()` has one line fewer than `end_line - start_line + 1`. `validate_context` then raises `PT-PROVIDER: invalid context ownership or evidence`. `persistence.validate_project` calls the same validator (persistence.py:103-104), so any saved interpretation for that context is refused too.
- Repro (run): function code `'int f(void)\n{\n  return 0;\n}\n\n'`, `build_context(p, [match.id])`, then `validate_context(ctx)` fails. The evidence record is `(1, 5)` but its text ends `'return 0;\n}\n'`. `validate_project` on a project with that interpretation also fails.
- Effect: AI interpretation is impossible for those functions, with a message that does not name the cause. No data is corrupted.
- Fix: split the text on `'\n'` in both places, or count lines with the same function in both. Keep persisted evidence text unchanged, so the change is additive. Red test: `build_context` plus `validate_context` on code ending in `\n\n`, and a `validate_project` round trip. No test in `tests/` covers this (grep found no `build_context` test with a `\n\n` code literal).

### CORE-2 (Medium): duplicate upstream entries double count shared evidence

- File: `src/patchtrace/normalization.py:76-94` (modified loop) and `:91`. Nothing checks for a repeated entry in `functions.added`, `functions.deleted` or `functions.modified`.
- Evidence: each `FunctionRecord` gets a fresh UUID (models.py:23), so `validate_project` never sees a duplicate ID (persistence.py:86-92). The same old function therefore appears in two matches.
- Repro (run): `raw['functions']['modified']` holds the same entry twice. `normalize_ghidriff` returns 2 matches, both with `older[0].address == '0x1000'`, and `validate_project` accepts the candidate.
- Impact: the product invariant "shared-origin evidence counts once" is broken for hostile or malformed upstream output. Counts shown by the UI and reports would inflate. No averaging or invented numbers are involved, so this is Medium, not High.
- Fix: in `normalize_ghidriff`, key each side by `(side, address, name)` (or by the upstream record identity) and reject a repeated key with `PT-SCHEMA`. Red test: a raw file with two identical modified entries must fail to normalize. Optionally add a `validate_project` rule that a function's upstream key appears in at most one active match.

### CORE-3 (Medium): a second import silently replaces every earlier match

- File: `src/patchtrace/service.py:210-211` (`candidate.runs = [...] + [owned_run]`, `candidate.matches = list(owned_matches)`).
- Evidence: `apply_import` replaces the whole `matches` list, not the matches of the run being imported. Earlier runs stay in `runs` with status `completed`. Their analyst overrides are marked stale by `_invalidate` (service.py:93-100) and are not restored.
- Repro (run): apply run A (1 match), then apply run B from the same raw file. Afterwards `matches` has 1 entry, all with run B's ID, and run A still reads `completed`.
- Impact: prior relations and manual corrections disappear without any warning, and the project still shows run A as a successful analysis. This conflicts with "keep conflicting evidence", and with the spec wording that prior results are preserved (architecture.md, `run_comparison` row, only on failure).
- Decision needed from the owner: either keep earlier runs' matches (with a run filter), or mark earlier runs `superseded` and say so in the UI. Until then the current behaviour is undocumented. The raw JSON of run A is still on disk, so the loss is recoverable by re-import.

### CORE-4 (Low): reference resolution is a full scan per reference

- File: `src/patchtrace/evidence.py:30-33` (`_related` filters `functions.values()` for every name reference), called from `evidence.py:63`, `:74`, `:172` and `persistence.py:129`.
- Measured (run, `repro_perf.py`): build_context with 10 selected matches and 10 references each: 0.16 s at 500 pairs, 0.59 s at 2000, 1.06 s at 4000. With 60 references per function and 3 selected matches: 1.23 s at 4000 pairs. `validate_project` on one saved context adds 0.45 s at 4000 pairs with 10 references, and 0.71 s with 60. Every save and load runs this check.
- Impact: cost grows with references times functions. Hostile input can raise the reference count without a cap (`FunctionRecord.callers`/`callees` have no length limit). Low because the measured numbers are moderate and the snapshot is file-bounded.
- Fix: build a per-run index `{(run_id, artifact_id, name_or_upstream_name): [funcs]}` once in `build_context` and `validate_project`, and cap callers/callees per record.

### CORE-5 (Low): an empty correction fails with the wrong error contract

- File: `src/patchtrace/service.py:284-301`. The check for an empty selection is missing; the failure comes from `FunctionMatch`'s validator at line 298.
- Repro (run): `svc.correct_match(match_id, [], [], 'modified', 'reason')` raises `1 validation error for FunctionMatch: Match must contain at least one function`. The project is unchanged, but the message is not `PT-SCHEMA: ...`, which the UI and CLI map from that prefix.
- Fix: reject `not older_ids and not newer_ids` with `PT-SCHEMA: correction must select at least one function` before building the candidate. Red test on the message prefix.

### CORE-6 (Low): preparing the same run twice orphans a raw copy

- File: `src/patchtrace/service.py:194-195` overwrites `self._prepared[run.id]` without discarding the previous staged path; `discard_import` (218-232) only looks at the current entry.
- Repro (run): `prepare_analysis(raw, run)` twice with the same run, then `discard_import` on both. `runs/<id>/raw/result.ghidriff.json` remains and nothing references it. The second preparation sees the file already present, so it stages nothing.
- Fix: at the start of `_prepare_analysis`, discard any existing entry for `run.id` (keeping its staged path cleanup), or refuse a second preparation of the same run. Red test: prepare twice, discard both, assert no file under `runs/<id>/raw/`.

### CORE-7 (Low): a read-only open writes to the project

- File: `src/patchtrace/persistence.py:489-494` (`load()` marks interrupted runs `failed` and calls `save`), `src/patchtrace/service.py:60-70` (`open(maintenance=False)` is documented as "read-only readers (series)"), and `persistence.py:285` (every `ProjectStore` takes the exclusive `ProjectLock`).
- Repro (run): a project with a `running` run, opened with `ProjectService.open(root, maintenance=False)`, then reopened: the status is `failed` on disk after the reader closes. Callers: `nway/series.py:43`, `nway/pair_access.py:71`, `fabric/cli.py:79`, `rules/cli.py:168`.
- Impact: a series or rules reader can change the project, and every reader excludes the GUI through the lock. The write is arguably correct recovery, but the name and docstring say otherwise.
- Fix: give `load()` a `recover: bool` parameter that defaults to True. Read-only callers pass False and report interrupted runs in memory only. Decide whether readers should take a shared lock. Test: reader leaves the stored status unchanged.

### CORE-8 (Low): `redact_log` mishandles a zero or negative limit

- File: `src/patchtrace/diagnostics.py:59` (`return text[-limit:]`).
- Repro (run): `redact_log('secret-free text', 0)` returns all 16 characters. A negative limit slices from the wrong end. No current caller in `src/` passes 0 (backend.py:331, 425, 606, 635; cli.py:868 use the defaults or positive values).
- Fix: `if limit < 1: raise ValueError(...)`, or `text[max(len(text) - limit, 0):]`. Red test for `limit=0` and `limit=-5`.

### CORE-9 (Low): dead alias and a schema-only model

- `src/patchtrace/alignment.py:64` (`align_code = align_lines`): no reference in `src/` or `tests/`.
- `src/patchtrace/models.py:43-49` (`BackendCapabilities`): no reference in Python; it appears only in `docs/schemas/BackendCapabilities.json`, `docs/schemas/examples.json` and `docs/specs/schemas.md`. Removing it changes the published schema set, so this is an owner decision.
- Fix: delete the alias. For the model, either remove it with its schema and spec row or add the code that writes it.

### CORE-10 (Low): a non-PE input is fully copied before it is rejected

- File: `src/patchtrace/ingestion.py:129-152`. The stream is copied to `artifacts/.input-*` in 1 MiB chunks (up to 1 GiB), `fsync`ed, and only then passed to `validate_pe` at line 152.
- Impact: wasted I/O and disk for obviously invalid files. Not a correctness issue, because the staged file is removed on failure.
- Fix: run the DOS/PE header checks on the first 64 KiB of the open source before copying (keeping the full `validate_pe` after the copy), so a non-PE file is refused before any bytes are written.

### CORE-11 (Low): persisted text and metadata have no length bound

- Files: `models.py:28` (`Artifact.name`), `:55` (`FunctionRecord.name`), `:58` (`code`), `:62` (`metadata: dict`), `:164` (`AnalystAnnotation.text`), `:182` (`AnalysisRun.settings`); `service.py:277-282` (annotations) and `:268-275` (`analyst_conclusion`).
- Evidence: the models accept any length. The only bound is the 256 MiB snapshot cap (persistence.py:30, 369). Report export caps names at 512 and text at 8192-16384 characters (`docs/specs/report-export-contract-v2.md:94`), but only at export.
- Impact: a single hostile record can take most of the snapshot and slow every load and save. Not a correctness break.
- Fix: add `max_length` to the persisted text fields (additive for existing data where the current maximum is smaller, which must be checked against stored projects first), and cap `metadata` size.

### CORE-12 (Low): spec row says backup copies fewer directories than the code

- Spec: `docs/specs/program-e/WB1-integration-plan.md:35` (F21) says `ProjectStore.backup` copies only the DB, `artifacts/`, `runs/` and `exports/`.
- Code: `persistence.py:524` also copies `kb` and `intelligence`, as the comment at lines 522-523 says (KB plan A-6).
- Fix: update the F21 row (documentation only).

## Suspicions (not counted; no repro on Linux)

- S1. `ingestion.py:118` calls `file_fingerprint` before the regular-file check at 119-120. On Windows `file_fingerprint` opens the path (ingestion.py:54), so a device name such as `CON` or `NUL`, or a named pipe, could block. Needs a Windows run. Suggested order: `stat`, check `S_ISREG`, then fingerprint.
- S2. `jobs.py:311-312`: on POSIX the `RLIMIT_AS` cap is applied with `prlimit` after `Popen` returns, so the child can allocate uncapped for a short window. The docstring (jobs.py:245-249) describes this trade-off only partly. Needs a timing test.
- S3. `jobs.py:330-341`: `terminate()` sends `killpg` after the child has been reaped by `poll()`. A reused process group ID is possible in theory.
- S4. `interpretation.py:257`: `interpret()` takes no consent argument; upload consent is enforced only by callers (`ui.py`, `providers.py`, not reviewed here).
- S5. `persistence.py:366-371` and `:404`: each save serialises and re-parses the whole snapshot (up to three full passes). Not measured.
- S6. `models.py:151`: `InterpretationRun.endpoint` is stored in the project. Architecture requires URL credentials to be rejected (SPEC-41 R11); not checked in `providers.py`.
