## Project definition

App name: PatchTrace.

Working tagline: Compare binaries. Trace fixes. Investigate flaws.

The name is provisional. Repository existence does not establish trademark or domain availability.

Category: Local-first desktop application for binary comparison, patch review, and evidence-based investigation of software bugs and vulnerabilities.

Primary goal:
Compare an older compiled software version with a newer version, display corresponding code side by side, and analyse changes to investigate what bug or vulnerability the patch may have addressed.

The proposed foundation combines:

1. Ghidriff for Ghidra-backed binary analysis, function matching, and difference extraction.
2. Suitable Diffalayze components for optional LLM-assisted interpretation and synthesis.
3. PatchTrace-owned UI, normalized contracts, project persistence, evidence registry, and analyst review workflows.

Reuse verified upstream capabilities. Concentrate original development on integration, usability, traceability, and reliable review.

The application must distinguish:

- Changes directly observed by analysis tools.
- Model-generated hypotheses.
- Analyst conclusions.
- Supporting and contradicting evidence.
- Unknowns and missing context.
- Review status.
- Separately supplied validation evidence.

A patch may be a security fix, ordinary bug fix, feature change, refactoring, compiler-generated difference, or an unresolved mixture. Do not assume changed code represents a vulnerability.

## Platforms, audience, and delivery

Initial application platform: Windows 11 x64.

Initial target artifacts: PE x86-64 executables, DLLs, and driver binaries, inspected statically. Parsing a driver must not install or load it.

Design portable boundaries for later Linux application support and additional formats. Windows x86, ELF, ARM64, and Mach-O are deferred unless research supports a low-cost addition without weakening the initial release.

Audience:

- Vulnerability researchers.
- Reverse engineers.
- Malware analysts.
- Incident responders.
- Product security teams.
- Native software maintainers.
- Experienced system administrators.

Initial collaboration model: one local analyst per project.

Delivery context: one developer assisted by coding LLMs.

Prefer free and open-source dependencies. Require no mandatory paid analysis engine, cloud account, or AI subscription.

First release: Windows standalone beta with a complete comparison and review workflow.

“Standalone” means a packaged desktop application. Research whether Java, Ghidra, Python, and other runtimes should be bundled or installed separately. Explicitly distinguish the desktop package from its required analysis dependencies.

No fixed schedule or hardware minimum has been supplied. Propose hardware classes, measurable targets, and dependency-aware milestones. Do not invent benchmark results or imply large binary analysis is inexpensive.

## End-to-end integration workflow

### Stage 1: Project creation and ingestion

The analyst explicitly selects older and newer artifacts.

Validate supported formats and architectures. Hash and identify inputs, preserve originals, capture metadata, and create a comparison project.

Define policies for:

- File-size and parser limits.
- Duplicate artifacts and identical binaries.
- Unreadable or changing files.
- Symbols and optional supporting documents.
- Unicode paths, long paths, and workspace permissions.
- Ownership and copying of artifacts.
- Storage exhaustion.
- Unsupported and incompatible pairs.

Record analyst-selected orientation. Never infer older/newer solely from filenames, embedded version information, or timestamps.

Swapping orientation must invalidate dependent interpretations and identify which artifact analysis can be reused.

### Stage 2: Ghidriff/Ghidra worker

Run analysis in a separate process so the desktop stays responsive and backend failure is contained. Process isolation is not a security sandbox.

Prefer native Windows execution if verified practical. Docker may be an optional backend.

Specify:

- Backend discovery and version compatibility.
- Safe argv construction without shell interpolation.
- Worker protocol and event schemas.
- Workspace and artifact ownership.
- Analysis settings and reproducibility.
- Log capture and redaction.
- Determinate versus indeterminate progress.
- Cancellation and process-tree cleanup.
- Timeouts and enforceable resource limits.
- Exit codes and failure classification.
- Partial-result quarantine and inspection.
- Retry and recovery.
- Cache reuse and invalidation.
- Atomic publication of completed outputs.

Do not assume Ghidriff already supplies reliable progress, cancellation, or every required evidence field. Identify adapter work and any minimal upstream changes.

Define Windows process cleanup concretely, including child processes and any required Job Object behavior.

### Stage 3: Normalization

Convert upstream outputs into PatchTrace-owned, versioned contracts.

The UI and interpretation pipeline must consume these contracts rather than arbitrary Ghidriff JSON.

Preserve raw outputs and upstream provenance.

If required function addresses, instruction references, cross-references, or code mappings are absent, specify the smallest additional Ghidra extraction step.

Represent missing evidence explicitly. Do not invent instruction-to-decompiler mappings or imply a decompiled line corresponds precisely to an instruction without verified mapping data.

### Stage 4: Comparison and manual review

Render function matches and code differences through normalized presentation models.

Allow analysts to inspect, reject, and correct matches before interpretation.

Persist manual decisions with provenance. Define their interaction with reanalysis and ambiguous, split, or merged functions.

### Stage 5: Diffalayze-derived interpretation

Inspect suitable Diffalayze provider and staged-analysis components.

Adapt the workflow for user-supplied binary comparisons. Automatic acquisition must not be required.

Choose whether each reused component is imported, wrapped, extracted, or minimally forked. State exact source boundaries and attribution obligations.

Separate acquisition, interpretation, provider access, UI, and project ownership.

Do not carry over automatic command execution triggered by model-generated severity.

AI is optional. Offline comparison and manual review must remain usable without model configuration.

Specify one local-provider path and one remote-provider path. Document verification evidence accurately. If live verification is unavailable, provide executable acceptance procedures and mark the path unverified.

Remote transmission requires an explicit analyst choice and context preview.

### Stage 6: Validation and persistence

Parse interpretation output into a strict schema.

Validate evidence IDs against the exact supplied context. Validate their artifact, run, side, and location associations.

A valid citation establishes traceability, not interpretation correctness.

Reject or visibly mark malformed output, unsupported references, and ungrounded claims. Preserve raw model text separately without promoting it into accepted findings.

Persist:

- Structured findings and hypotheses.
- Review status and annotations.
- Provider and model configuration, excluding credentials.
- Prompt and schema versions.
- Context identity and digest.
- Relevant analysis settings.
- Truncation and limitations.
- Timing, usage, and retry metadata where available.

### Stage 7: Reporting

Generate Markdown, self-contained HTML, and versioned JSON reports from persisted project data.

Distinguish observations, model hypotheses, analyst conclusions, and validation evidence.

Define deterministic report selection, provenance, redaction, manifests, and error behavior.

## Interpretation behavior

For each selected change investigate:

1. What changed?
2. What did the older code appear to do?
3. How does the newer code alter behavior?
4. Which bug or vulnerability hypothesis best explains the change?
5. Which alternative explanations remain plausible?
6. Which preconditions would be necessary?
7. Is relevant input influence established or unknown?
8. Is reachability established or unknown?
9. Which evidence supports or contradicts the hypothesis?
10. Which inspection or reproduction would resolve uncertainty?

Require:

- Change summary.
- Proposed fix purpose.
- Bug category.
- Optional CWE mapping and rationale.
- Affected functions and paths.
- Supporting evidence.
- Counterevidence.
- Preconditions.
- Unknowns.
- Alternative hypotheses.
- Suggested verification steps.
- Analyst review status.

Do not invent CVE attribution, affected version ranges, attacker control, exploitability, or severity.

Use changed functions and relevant caller/callee context within a bounded budget. Avoid isolated interpretation when behavior depends on related functions.

Specify:

- Context selection and ranking.
- Cross-reference depth and expansion.
- Handling of missing code.
- Token estimation and budgeting.
- Truncation and visible omission records.
- Batching and deduplication.
- Cache keys and invalidation.
- Provider limits.
- Retry policies and bounded repair attempts.
- Rate limits and cancellation.
- Cost estimation with clearly stated assumptions.
- Context preview.
- Provider response validation.

Do not claim omitted context is harmless. Preserve a record of what was selected, excluded, unavailable, or truncated.

Treat artifact text, imported documents, code comments, and model output as untrusted data. They cannot authorize tools, commands, or changes to analysis policy.
