# Prompt for ChatGPT: per-panel Qt UI specs and the panel plan

How to use: open a new ChatGPT conversation, attach (or paste) these repository files: `docs/specs/program-e/GUI-integration-plan.md` (sections 7-9), `docs/specs/gui-framework.md`, `docs/specs/ui.md`, `docs/specs/program-e/<ID>-integration-plan.md` for CAP, DIE, KEV, YRX, WB1, WB2, WB3, KB, PIL, WBQ and `docs/specs/unified-engine/07-ui-and-cli.md`, plus `docs/modules.md` sections for `gui/qt`. Paste the prompt below. Save each returned spec as `docs/specs/panels/<panel-id>.md` and the plan as `docs/plans/panels-build-plan.md`, then tell Claude.

---PROMPT---
You are a senior desktop UI architect and specification writer for PatchTrace, a Windows-first Qt (PySide6 6.12) application that compares an older and newer build of a Windows PE binary to find the code a patch changed. The application has one main window; every feature is a dock panel hosted by a panel framework that already exists in the repository (slices F0-F9, attached): PanelSpec and PanelController contracts, PanelContext ports (ProjectPort, MutationPort, NavigationPort, ShellPort), TaskRunner with lanes and CancelToken, StateView (loading, empty, blocked, error, stale), VirtualTable (virtual, sortable, filterable, copy-capped), CodeDiffView, GraphCanvas, chips, ThemeTokens (dark, system, high contrast, reduced motion), tooltip registry (What/Why/Effect/Source lines), accessible names, keyboard shortcuts Ctrl+Shift+<letter>, anchors (AnchorRef kinds) and navigation history.

Product invariants you must respect in every spec: never execute a target binary; never upload anything without operation-specific consent and an exact preview; never fabricate unavailable evidence; never show an uncalibrated number as vulnerability confidence; never average different engines' scores; keep conflicting evidence; unknown is not a negative vote; shared-origin evidence counts once; older/newer orientation is explicit; provenance on everything; advisory, string and code text is untrusted (bound, escape, never execute); one main window (docks/tabs only, no extra top-level windows); pure models and adapters stay separate from Qt; persisted contracts change additively only; Microsoft-derived binaries and labels are never committed; no GPL/AGPL code is copied.

Task. Write one implementation-ready spec per panel for these panels, in this order: (1) unified (UE S4b, exists: only reconcile), (2) leads (PIL C2, exists: reconcile), (3) kb (K4b dock and the six K7 online pages), (4) capabilities (CAP-6a/b), (5) search (WB1 S7), (6) kev (K3), (7) build_env (DIE D5), (8) graph (WB2 G5/G6), (9) strings (WB3 S7b), (10) rules (YRX R6b), (11) pe meta tab and code text (WBQ S6/S9 wiring into Files and the diff panes), (12) series and files (already migrated: reconcile), (13) guide (deferred: one-paragraph stub only), (14) any panel the attached plans imply that is missing (list it and justify).

Each spec must contain exactly these sections: 1 Purpose and users (one paragraph, the analyst question it answers). 2 Position and identity (panel id, title, area, tab group, shortcut, focus order, default_visible, requires capabilities, claims profile). 3 Data contract (the pure view-model fields, with types and limits; what the service provides; no Qt). 4 Layout (regions, widgets from the framework, column tables with header text, widths in em, sort defaults, filters, empty-cell text). 5 States (a table of every state with trigger, exact on-screen copy, remedy button, announcement text; use the framework state names). 6 Interactions (actions, buttons, keyboard map, context menu, selection behaviour, copy behaviour, drag and drop if any) with exact command ids. 7 Navigation (anchors in and out with kinds, what happens on stale, ambiguous or missing anchors). 8 Threads and cancellation (which tasks run in which lanes, what is cancellable, progress text, generation handling, what runs on the GUI thread). 9 Settings (keys, defaults, ranges; keys under `<id>/`). 10 Tooltips (every tooltip id with the four lines What, Why, Effect, Source; at most 160 chars each for What). 11 Accessibility (accessible names and descriptions for every control, tab order, screen-reader announcements, high-contrast and reduced-motion behaviour, no colour-only meaning). 12 Performance budgets (rows, nodes, time to first paint, memory; numbers). 13 Security and privacy (hostile text handling, consent flows, network calls and their exact hosts, what is never shown). 14 Test plan (named tests: every state, hostile text, a11y audit, data() gates, teardown, anchors, 20x repeat gate, manual Windows checks as a separate list). 15 Open questions with a default for each (none may block the build).

Then write `panels-build-plan.md`: dependency order of the panels, which pure view-models must exist first (name the module and function), shared widgets still missing from the framework (name them and say which framework slice should add them), estimated size (S/M/L) per panel, and the risks. Keep each spec under 400 lines; be precise, avoid marketing language, use plain scalars (no ': ' inside YAML), use exact identifiers from the attached files, and when the attached files conflict, list the conflict and choose one with a reason. Do not invent features that are not in the attached plans; propose them only under Open questions.
---END PROMPT---
