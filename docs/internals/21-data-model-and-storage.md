# 21. Data model and storage

What a project is on disk, which records are persisted, how derived data is kept beside it without mutating evidence, and which rules keep persisted contracts stable. Sources: `src/patchtrace/models.py`, `persistence.py`, `verified_backup.py`, `service.py`, `enrichment/{identity,storage,contracts}.py`, `docs/schemas/`. Previous: [20 architecture](20-architecture.md). Next: [22 engines and fusion](22-engines-and-fusion.md).

## Project directory

```
<project>/
  project.sqlite3            current snapshot, bounded history, enrichment tables
  .patchtrace.lock           kernel advisory lock (msvcrt / fcntl): one writer
  artifacts/<sha256>.bin     read-only immutable copies of the two inputs
  runs/<run_id>/raw/         result.ghidriff.json + analysis.log (project-owned, single copy)
  runs/<run_id>/unified/     results/<id16>/{manifest.json, rows.jsonl.gz, facts.jsonl.gz} and ir/<key>/ir.sqlite3 (SPEC-31 D-06, D-07)
  runs/quarantine-<id>/      failed or unverified output; never published as a run
  exports/                   report files and manifests
  intelligence/              CSAF source snapshots; intelligence/pilot/<id>/ patch-intent results
  kb/                        KB investigation sidecars
  backups/                   verified SQLite backups taken before any pruning
```

Every path is resolved through `safe_path(root, ...)`, which refuses traversal and symlink escape. Copied artifacts and raw outputs are made read-only (Windows needs the read-only bit cleared before deletion, handled by `_clear_readonly_and_retry`). Backup (`ProjectStore.backup`) copies the SQLite file through the SQLite backup API plus `artifacts`, `runs`, `exports`, `kb`, `intelligence`; it refuses a symlink anywhere and publishes without replacing.

## Core records (`models.py`, contract version 1)

All records derive from `Record`: pydantic **strict**, `extra='forbid'`, `validate_assignment`, `schema_version: Literal[1]`, an `id` (default `uid()`, 1 to 128 characters).

| Record | Key fields and invariants |
|---|---|
| `Artifact` | `side` older/newer, `name`, `sha256` (64 hex), `size` 1 to 1 GiB, `relative_path` (must stay relative), `architecture='x86-64'`, `format='PE'` |
| `AnalysisRun` | `status` (queued, running, completed, failed, cancelled, identical), `backend` (default `ghidriff`) and `backend_version`, `settings` dict (symbol policy etc.), `raw_path`, `raw_sha256`, `error`; `BackendCapabilities` (name, version, decompiler, instruction mapping, progress counts, limitations) describes an engine |
| `FunctionRecord` | `artifact_id`, `run_id`, name, address and `address_space` (virtual, relative, file-offset, unknown), code, assembly, callers, callees, metadata |
| `FunctionMatch` | `run_id`, older/newer lists, `category`, `match_types`, `quality` text, `manual`, `reason`, `review`. Validators: at least one function; `added` has only newer, `removed` only older |
| `DiffHunk`, `EvidenceReference`, `AnalysisContext`, `Hypothesis`, `Finding`, `InterpretationRun` | AI interpretation chain: a context holds evidence with artifact/run ownership; a finding may cite only evidence of its context |
| `AnalystAnnotation` | `target_id`, `kind` (`note`, `bookmark`, `match-override`, `validation`), text, `stale` |
| `JobEvent`, `ExportManifest` | log rows (`run_id`, stage, message, progress 0 to 1); report manifests (format md/html/json, SHA-256, finding ids, include flags) |
| `ComparisonProject` | name, `revision`, exactly two artifacts (one older, one newer), runs, matches, interpretations, annotations, `sample` flag |

`ComparisonProject.relationships` is the ownership firewall: unique ids, every match belongs to an existing run, every function's `artifact_id` has the right side and its `run_id` equals the match's, a context's `project_id`/`revision` agree with the project, evidence owners exist (side check relaxed only for stale contexts), and a finding cites only evidence in its own context. Forged ids fail at load, not later.

JSON schemas for these are generated by `tools/generate_schemas.py` into `docs/schemas/*.json` and compared by a regenerate-and-compare test; each feature package has its own generator (`generate_fabric_schemas.py`, `generate_kev_schemas.py`, `generate_pilot_schemas.py`, `generate_rules_schemas.py`, `generate_kbc_schemas.py`, `generate_intelligence_schemas.py`, `generate_intel_tools_schemas.py`).

## SQLite snapshots (`persistence.py`)

- `PRAGMA user_version = 1` (`SCHEMA_VERSION`); a different non-zero version is refused. Tables `current_snapshot` (singleton) and `history` (append-only per save).
- A snapshot is one canonical JSON document, strictly parsed (`strict_json`: duplicate keys, NaN/Infinity and overflowing numbers rejected). Cap `MAX_SNAPSHOT_BYTES` 256 MiB.
- **History bound.** Keep the newest `HISTORY_KEEP = 100` rows and at most `HISTORY_MAX_BYTES = 512 MiB`, never pruning the current snapshot or the newest snapshot of each revision. **No backup, no deletion**: rows are pruned only after a re-opened, integrity-checked `backups/project-pre-history-prune-*` backup exists (`verified_backup.py`); if it cannot be made, the save still commits and every row is kept.
- **Single writer.** The lock is held for the life of the open store; a crash releases it. The lock file records pid and host for diagnostics only.
- **Service.** `ProjectService` is the only mutator: `create`, `open`, `import_diff` / `apply_analysis` (prepare on a worker, apply on the owner), `review_match`, `review_finding`, `annotate`, `correct_match`, `restore_match_override`, `swap_orientation`, `add_interpretation`, `backup`. A candidate snapshot is validated and committed before publication; failed or cancelled attempts record a terminal run without touching earlier results.
- **Stale rules.** Orientation swap or correction invalidates interpretation contexts (`_invalidate`), which then display raw context but never navigate.

## Identity (`enrichment/identity.py`)

Content identities are reproducible on every platform: strings NFC-normalized, keys sorted, compact separators, **floats and NaN rejected** so a score input cannot drift. `domain_id(domain, version, payload)` = SHA-256 of `b'patchtrace\x00' + domain + 0x00 + version + 0x00 + canonical_json(payload)`. Timestamps and absolute paths are never passed in. Each feature owns its domains (`diff`, `occurrence`, `pairing`, `signal`, `stage` for enrichment; `series`, `anchor`, `pilot`, ... elsewhere). Fusion and unified keys use integers only (determinism: inputs sorted by RVA, no set iteration without sort).

## Enrichment tables (`enrichment/storage.py`, additive)

`user_version` stays 1: v1 code only reads `current_snapshot` and `history`, so extra tables are invisible to it. Tables: `enrichment_meta(key, value)` and `enrichment_entries(id, kind, project_id, project_revision, run_id, raw_sha256, input_digest, status, stale, created, body, body_sha256)` with an index on `(kind, run_id)`.

- **Guard.** Each row records what it was computed from (`project_id`, `run_id`, `raw_sha256`, `input_digest`). A worker computes an immutable body; `publish` rechecks the guard immediately before commit, and a result whose guard no longer holds is stored `stale`, never current.
- **Extension version.** `EXTENSION_VERSION = 2`; new stores are stamped 1 and are raised to 2 only when a v2-only row (`engine-run`, `secondary/2` sets) is first written, so older clients keep access to projects that never used SPEC-28.
- **Closed set of kinds** (`KINDS`): `signals`, `ranking`, `wil`, `cve-snapshot`, `contextual`, `pipeline`, `secondary-matches`, `engine-run`, then reserved and later: `unified-run`, `unified-result`, `advisory-source`, `advisory-facts`, `tool-run`, `tool-evidence`, `patch-intent`, `kb-investigation`, `kb-context`, `kev-context`, `search-saved`, `rule-candidate`, `rule-decision`, `rule-version`, `rule-test`, `rule-export`, `anchor-batch`, `anchor-pin`. Adding a kind is a shared-file change (integrator only).
- **Retention.** Only `DERIVED_KINDS = signals, ranking, wil, contextual, pipeline` are ever deleted (recomputable): keep 8 current and 2 stale generations per profile, orphans after a 5-minute grace. Imported evidence (`secondary-matches`), `cve-snapshot`, engine runs (newest 8 per engine/older/newer group) and every other kind are never evicted. Caps: 32 MiB per row, 128 MiB total.
- **Thread rule.** Every store method runs on the thread that owns the project connection; workers hand immutable bodies back.
- **Sidecars for big results.** Unified rows, IR databases and pilot assessments are files (content-digest named, manifests with part hashes) under `runs/<run_id>/unified/` and `intelligence/pilot/<id>/`; the database holds tiny pointer rows. They are copied by backup because they live under `runs/` and `intelligence/`.

## Derived cache (outside the project)

`enrichment/cache.py` is an optional, content-addressed global cache selected by a profile's `cache_dir`: derived stages and raw Ghidriff output. An entry is served only after its manifest parses and its hash verifies; budget `cache_budget_gib` (default 20); `cache status|verify|prune` maintain it. Raw-cache reuse is opt-in and recorded in the run.

| Calibration artifact | read-only, digest-checked | `patchtrace-calibration-model/1`; none ships |

## Contract rules

1. Every contract is versioned `name/N`. Readers refuse unknown versions and ignore unknown *additive* fields only where the contract says so.
2. **Changes are additive**: a new optional field appended with a default; nothing removed, renamed or retyped. Breaking changes need a new version and a spec first (`AGENTS.md`).
3. Strict validation at every boundary: duplicate keys, coerced booleans and extra fields are errors. Untrusted text goes through `hostile_text` (control, format, bidi, zero-width, surrogate code points removed or replaced per sink).
4. Persisted records never hold credentials or absolute source paths meant for export; exports redact paths.
5. Microsoft-derived binaries, PDBs and Winbindex-derived labels are never committed to the repository.
