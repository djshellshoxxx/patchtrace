# R2 native rz-diff: conditional side reversal and fixture-analysis failures

2026-10-30. Research baseline `a04f5a299a8d4afef023261e52e08d14678cf1e7`; native probe/evidence commit `b6e0edf`. This note documents source investigation and native observations. It changes no production adapter, parser, acceptance policy or installed tool.

**Finding:** pinned rz-diff 0.9.1 reverses the meaning of JSON `original` and `modified` when input0 has exactly one **recovered Rizin function**. Its ordinary multiple-function branch retains the supplied order. PatchTrace currently interprets `original` as older unconditionally. Both branches were exercised through production execution/parsing. A global swap would repair the singleton example while breaking ordinary runs.

The same smoke also found twenty cases where native analysis recovered no file0 functions, returned exit code zero with empty stdout, and was correctly rejected by PatchTrace's strict parser. Those failures are recorded as failures, not valid zero-accuracy runs. They do not establish the cause of every function-discovery limitation.

## Five appended diagnostics and conditional source proof

In the address-shift fixture, image base is `0x180000000`. The expected helper relation is old `0x1010` → new `0x1050`; the caller relation is old `0x1000` → new `0x1040`. Native rz-diff reports only the helper, labeled `sym.synthetic.dll_helper`, with similarity 1.0/COMPLETE. Its `original` address is `0x180001050` and `modified` is `0x180001010`: new then old, despite older then newer argv. These addresses are outside the respective fixture's known entry sets, so the probe leaves them unknown rather than quietly repairing them.

| Diagnostic | Supplied input0/input1 | Native JSON observation | Meaning |
|---|---|---|---|
| shift-forward | Old address-shift image / shifted new image | `original=0x1050`, `modified=0x1010` | Reversed relative to argv |
| shift-reverse | Shifted new image / old image | `original=0x1010`, `modified=0x1050` | Again reversed relative to argv |
| one-recovered-vs-two | Nuisance old image / split newer image | `original=head,tail`; `modified=helper` for both rows | Input0 singleton triggers reversal |
| two-recovered-vs-one | Split newer image / nuisance old image | Same head/tail → helper rows | Now correct relative to argv |
| two-recovered-vs-two | Split newer image / merged older image | head → head, tail → tail | Ordinary multi-function branch |

The two unequal-count diagnostics deliberately compare existing images with different roles. They test side attribution and branch behavior, **not matching accuracy between unrelated source transformations**. Recovered function counts in this table are the branch interpretation supported by the returned helper/head/tail rows and pinned source, not the authored fixture function counts. The authored caller entry is absent from the native function proposals. Source-level function count, PE export count and Rizin recovered-list cardinality are not interchangeable.

Pinned primary files, retrieved at `v0.9.1`:

* [Matching implementation](https://github.com/rizinorg/rizin/blob/c3a90e9226d977f58f4e9c75f78fa6b07afe13c7/librz/arch/similarity.c), Git blob `8544259e17a692bcb3c1d8858f104745cd0cba4c`.
* [CLI/serializer implementation](https://github.com/rizinorg/rizin/blob/c3a90e9226d977f58f4e9c75f78fa6b07afe13c7/librz/main/rz-diff.c), Git blob `3be455f898e91b906ed2d2307060f41c0833450e`.

`rz_analysis_match_functions`, matching file lines 568–574, tests whether `list_a` has one function. If so, it passes the two lists in reverse order to the singleton callback. That callback, lines 525–556, takes the original input0 function from its second list, visits original input1 functions from its queue, and creates each result pair with the input1 function first. It does not swap result fields back. The ordinary callback, lines 472–519, creates pairs in input0/input1 order. The CLI, lines 2042–2047 and 2211–2219, serializes `pair_a` as `original` and `pair_b` as `modified`. Together these explain the live conditional reversal without assuming a global side convention.

There is a second source-level explanation for exit-zero empty output: `core_diff_show`, a void function, exits when its file0 recovered function list is empty (CLI lines 2132–2164). Its caller later reaches the success assignment. This explains the observed status/document mismatch; it does not by itself explain why those tiny fixture functions were not recovered.

Neither a blind field swap nor an added `-B` is justified. A blind swap contradicts the observed 2→1 and 2→2 ordinary branches. For `-t functions`, CLI lines 2365–2385 already analyze both files unconditionally before matching. The generic help's description of `-B` does not make it the missing analysis step on this path. No alternate flags or patched-tool outputs are mixed into the initial evidence.

## Can existing production data establish orientation safely?

**Not in general.** At `secondary/rzdiff.py::parse_output`, the available inputs are native rows, version and caller-supplied artifact hashes. The JSON has names, addresses and sizes, but no source-file identifier, per-side hash or original recovered-list count. The hashes attached to `SecondaryMatchSet` label the invocation; they do not authenticate which input generated JSON `original`. `EngineJob` adds paths and configuration, but does not carry the producer's recovered functions or branch selection.

At unified ingestion, `AddressMap` has each artifact's verified PE image base and size. It validates VA/RVA basis and image-range membership, not function-entry ownership. Both images here have the same base and accommodate both shifted offsets, so the wrong addresses can pass that check. An address appearing in the other image's range is not proof of orientation, because patch pairs commonly overlap almost entirely.

Optional existing ProgramIR function tables, known Ghidriff endpoints, exports or `.pdata` entries can supply useful ownership counter-evidence. They cannot generally establish Rizin's exact recovered input0 count: a different analyzer may split, miss or invent boundaries; PE exports are incomplete; `.pdata` omits some functions; and the native serializer filters function types before writing rows. Therefore counting JSON rows, unique `original` addresses, export names or Ghidra functions does not reproduce the branch condition. The unequal-count diagnostics also show that a many-to-one JSON shape can arise from either branch.

One can conservatively reject a row when authoritative available data contradicts its claimed ownership. Automatically swapping because the reverse assignment fits better is a stronger claim: a false engine prediction, alias, repeated body or overlapping RVA can fit both hypotheses. Where both fit, existing output lacks the missing bit needed to select the side. Some individual distinct-base or exclusive-entry cases may be diagnosed with additional trusted constraints, but a generally safe detector must retain an explicit unknown outcome rather than generalize that success.

This assessment is source-based and limited to currently available metadata; it is not an impossibility claim about analyzing artifact bytes. Reimplementing Rizin's recovery to infer its branch would itself be new extraction. No production change was made without an orientation proof.

## Operational impact and safe repair options

Rz-diff atoms are tier W/E-BODY in the existing registry, so a reversed raw-byte proposal cannot independently satisfy A acceptance or cross-component B corroboration. This bounds one acceptance path; it does not make reversed identity harmless. `SecondaryAdapter._rzdiff` can still emit W candidate edges and side-specific display names for image-range-valid addresses. A conflicting W edge can create a weak contest on an otherwise stronger pairing. Secondary records, evidence links and function labels can point to the wrong artifact location. Affected stored sets retain caller-declared older/newer hashes, so pair ownership checks alone do not reveal the mistake.

Safe options for a subsequent authorized implementation are:

1. **Fail closed or quarantine unverified orientation for the affected producer path.** Preserve raw bytes, version and a classified limitation/error. Do not silently turn unknown side identity into a successful normalized set or let it produce misleading endpoint links. This is conservative and sacrifices usable multi-function runs unless a sound discriminator is added.
2. **Use a producer with explicit, verified side semantics.** An upstream fix can restore pair order and unmatched-list order at the singleton boundary, or emit per-side identity/cardinality metadata. Pin and independently regression-test the new artifact; the current `0.9.1` version string alone is insufficient to distinguish a locally patched build.
3. **Add an exact preflight for the producer's recovered input0 cardinality.** This requires new extraction with matching analyzer/configuration and adds time, cancellation, provenance and cache obligations. It must count the same pre-serialization list the branch uses, not exported or displayed functions. It is not available “for free” from the current parser inputs.

Evidence-guided rejection using already available trusted entries is useful as a narrower safeguard. It must not be described as a universal repair. An external upstream bug report would be appropriate only if separately authorized; no external message was sent. Existing cached sets need a migration/invalidation decision if side-normalization behavior changes; preserve their raw provenance instead of retroactively guessing orientation. Relevant secondary cache/config identities must distinguish old and repaired behavior.

## Regression design and acceptance boundary

A repair should first demonstrate a failing identity regression using the retained native JSON, not merely assert that some matches exist. Required cases are recovered counts 1→1, 1→many, many→1 and many→many, with arguments reversed as a separate run. Use disjoint side entry offsets and, where practical, distinct image bases so swapped ownership is observable. Include overlapping-RVA/name cases to prove ambiguous orientation remains unknown rather than guessed. Include unmatched rows and filtered function types; pair-field reversal alone may leave unmatched-list side labels inconsistent.

Parser/adapter tests should preserve artifact hashes, names, sizes, raw output SHA and source attribution, reject impossible ownership, and keep zero-exit empty stdout as a classified failure. Integration should verify no incorrectly oriented W atom, contest or evidence link escapes into unified output. Native tests must assert expected artifact/RVA identity, not only a nonempty function list or matching version. Keep N:M source transformations outside 1:1 scoring and do not force singleton all-against-one proposals into exclusive pair truth.

This slice ran no new full test suite because root owns integration testing. The probe passed Ruff and `git diff --check`; native compatibility itself remains failed for the recorded reasons. Linux native observations do not close Windows compatibility or large-binary resource gates.
