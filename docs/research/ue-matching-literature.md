Reading of the table [I]: all production differs share the same skeleton (ordered unique-key cascade, then neighbour propagation); they differ in (a) how long the weak tail is, (b) whether ambiguity is resolved by a global optimisation (QBinDiff, BinSlayer) or abstained, and (c) whether embeddings replace hand keys (DeepBinDiff, Asm2Vec, jTrans). Our ladder P01-P19 already covers (a) and (b) in a bounded form; (c) is out of scope for the core (R05 s6; D-25).

## 3. Concrete improvements for our ladder P00-P19 and fusion

Each item: idea, expected gain (qualitative, [I]; all must be measured on the 08 gates, no number here is a promise), cost (implementation + runtime), risk, source. Ordered by value per cost. IDs are new (I-xx) so the S2/S5 owners can cite them.

### 3.1 Ingest / key construction (feeds P04-P15)

**I-01 Fragment coalescing before any pass.** Idea: build logical functions by merging `.pdata` entries chained via `UNW_FLAG_CHAININFO` (and tagged funclets) into one function with multiple extents; compute `h0..h3`, `n_bb`, MD over the union CFG; keep chunk list for provenance. Gain: removes fake added/removed for hot/cold pieces and keeps P04-P10 working under PGO (FM-2/3/8). Cost: low (pdata parse in extractor; one pure merge step in ingest). Risk: wrong merge on non-PGO outlined code; if MSVC emits cold parts as independent functions (U) the step is inert; gate by `extent_src == pdata`. Source: https://learn.microsoft.com/cpp/build/x64-unwind-information-v3 [S]; R04 s6 [int].

**I-02 Idiom-normalised twin keys.** Idea: add second variants of `h3` and the MD keys computed on a canonical form with `/GS` cookie load/xor/check, CFG dispatch call (`__guard_dispatch_icall`), hotpatch padding and `sub/add rsp` immediates abstracted (frame class, D-33); keep the raw keys; a pair matched only by the twin is tier B with an extra hint `idiom-normalised`. Gain: restores P05-P11 hits when only instrumentation changed between builds (FM-6, FM-9), raising matched-by-strong-key share and shrinking the leftover set for P16-P19. Cost: low-medium (pattern table, test fixtures from the live clang probes). Risk: over-normalisation merges truly different functions; mitigated by uniqueness gate and tier B only. Source: LLVM CFGuard mechanisms [S]; Orange Cyberdefense anecdote [S]; R05 F15 [int].

**I-03 Block-merged flow graph MD ("straight-line collapsed") as a P10 variant.** Idea: collapse blocks with a single predecessor and single successor before computing `md_td/md_bu/n_bb/n_edge`, so compiler block splitting, tail merging or inserted check blocks do not change the key. Gain: P10 robust to cosmetic block splits; fewer P16/P19 residuals. Cost: low (BFS levels unchanged, quirks flag preserved). Risk: lower specificity; keep tier B, demote to C if G-U3 precision lower bound < 98 % (08). Source: BinDiff has "relaxed" MD variants and Diaphora files pure-graph rules under "unreliable" (heuristics #43-50) [F]; MD-index design in 04 s2.

**I-04 Thunk and wrapper collapsing before call-graph keys (P11, P13, P15).** Idea: replace callee ids with the final non-thunk target and import key before computing call-graph MD and callee sets; stable under CFG/XFG stubs and delay-load rewrites. Gain: P11/P13 hits survive stub churn; fewer `callee` deltas later. Cost: low. Risk: wrapper that gained logic is a real change: collapse only pure jump/tail-call thunks. Source: R05 F5 [int].

**I-05 Switch-aware CFG key.** Idea: for functions with recovered jump tables, key the multiset of successor block hashes (sorted) and the case count, never table bytes or the table-load displacement; add as part of the P10 gate or as a P10 sibling. Gain: removes layout noise from switch-heavy functions (FM-7). Cost: medium (needs table recovery quality from the extractor, D-33). Risk: failed recovery produces truncated CFGs; if recovery is flagged incomplete the key is NULL (no match, not a wrong match). Source: LLVM thread on `__ImageBase` switch lowering [S]; `/jumptablerdata` page [S].

### 3.2 Pass ladder and propagation (P04-P19)

**I-06 Make inline/outline evidence two-class.** Idea: accept an `inlined-into` group (04 s7) only when (a) >= 2 rare blocks of the older-only function are found inside one matched newer function AND (b) the call edge older caller -> that callee is absent in the newer function while the newer callee set shows no replacement. (a) is E-BODY, (b) is E-CALL, so the group satisfies D-32 without new components. Gain: fewer mislabelled removed/added; fewer false "inlined" claims from coincident small blocks. Cost: low (counters already in IR). Risk: the callee still exists elsewhere and the call was merely deleted by a patch; keep hint wording "possible". Source: inlining makes mapping 1-to-n / n-to-n https://arxiv.org/pdf/2112.12928 [S]; R05 F11 [int].

**I-07 Per-pass marginal-contribution ablation and pruning.** Idea: in the G-U3 report add for each pass the number of unique accepted pairs that no other pass would have found (leave-one-pass-out on Tier R) and its cost; remove or demote passes with zero marginal contribution on all corpora. Gain: shorter, faster, easier-to-reason ladder; Diaphora itself ships nine "Seems not to find anything?" rules [F], showing ladders accumulate dead weight. Cost: low (harness only). Risk: a pass useless on the corpus but valuable on Windows-specific samples; require Tier W confirmation before deleting, demote rather than delete. Source: Diaphora heuristics file comments [F].

**I-08 Order-preserving resolution of duplicate buckets (adaptive P18).** Idea: for content-identical buckets that drill-down and propagation did not resolve, find the unique order-preserving assignment between the two nearest matched anchors (longest monotone chain) and accept only if unique; enable per image only when the tier-A anchor order has Kendall tau >= configured threshold (measured, since PGO/LTCG destroy order). Gain: resolves template instantiation and thunk-clone families that currently become `duplicate` groups (FM-13); Diaphora's "same order and hash" and "same RVA and hash" rules sit in its best bucket [F], so the signal is real when layout is stable. Cost: low (LIS over anchors). Risk: ICF or PGO reorders silently: the tau gate and `C` tier only, and only inside a gap bounded by two anchors. Source: Diaphora heuristics #1-2 [F]; PGO layout [S].

**I-09 Data-reference edges in propagation.** Idea: add matched global/vtable/RTTI nodes as a second relation next to callers/callees: two unmatched functions referencing the same matched global (hub-capped by fan-in, L-17) vote like call-site votes. Gain: C++ virtual functions and table-driven code that have few direct callers; R04 notes PatchDiff2 and Ghidra's data-reference correlator do this [int]. Cost: medium (DATA-MAP already exists for L2). Risk: popular globals are hubs; fan-in cap and rarity weight needed. Source: R04 s6 and s8 [int].

**I-10 Rarity-ordered neighbour truncation.** Idea: when a neighbour set exceeds L-18, truncate by descending IDF of the candidate's keys (rare first) with rva as the tie-break, instead of rva order alone; keeps `limits_hit` recording. Gain: propagation spends its budget on informative neighbours, not on the lowest addresses. Cost: low. Risk: none to determinism if the tie-break is total. Source: [I]; rarity weighting is in R05 F9 [int].

**I-11 P19 upgrade: IDF-weighted similarity and one bounded flooding step.** Idea: replace plain Jaccard in 6.4 by IDF-weighted containment over the same tokens, and add one similarity-flooding-style term (similarity of the already-matched neighbours) inside each bucket, mixed by a fixed tradeoff, as QBinDiff's `--tradeoff` does between content and call-graph similarity; keep rejection cost and margin. Gain: better disambiguation among near-clones inside a bucket; still tier C. Cost: medium (k <= 200, cubic LAP unchanged). Risk: tuned tradeoff is a new hypothesis (02 s6.1); freeze on dev lineages only. QBinDiff's own warning that the normalised call graph can cause partial matching [F] argues for the bucket-local restriction. Source: QBinDiff README [F]; Similarity Flooding and BinSlayer's Hungarian step [S]; R04 s1 [int].

**I-12 Edge-preservation as a veto, not a score.** Idea: after the ladder fixpoint, for every accepted pair count preserved caller/callee edges under the current mapping; a tier-B/C pair whose neighbourhoods are mostly mapped to different counterparts gets hint `edge-inconsistent` and cannot count as corroboration in the D-32 test. This reuses QBinDiff's objective (edge preservation) as an ordinal diagnostic and never as a fused number. Gain: catches coincident-hash errors the uniqueness gate cannot see. Cost: low (one pass over CSR adjacency). Risk: patched regions truly change neighbourhoods; limit the veto to pairs with no tier A/M anchor. Source: QBinDiff objective (README, [F]); D-11.

### 3.3 Fusion and ranking

**I-13 Ordinal lattice, not RRF, for decisions; RRF only for ordering inside a verdict bucket.** Idea: keep rule-based decisions (D-11). For ordering review lists where several rank signals exist (delta severity class, size-normalised churn, attention rank from SPEC-30, N-way churn), use reciprocal rank fusion with k = 60 over per-signal rank lists after first collapsing correlated signals to one list per component. Gain: no calibration or score scale needed; Cormack et al. report RRF beats any single contributing system and Condorcet Fuse on TREC runs. Cost: very low. Risk: RRF assumes independent-ish rankers and has no notion of correlated duplicate lists (same overcount problem as D-32); never use for acceptance or `matched`. Source: https://research.google/pubs/pub36196/ and https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf [S, 2026-10-15].

**I-14 Typed-delta severity key as the primary rank, size as a tie-break.** Idea: rank `material`/`review` rows by (verdict, anchored delta class order, then fewer unrelated deltas), with classes ordered: callee changed to an unmatched target, condition/compare constant with branch, new block containing store/call, struct offset, string, constant (non-compare), register-only, frame. The learning-to-rank prior (R05 R10) can later replace the hand order once labels exist. Gain: puts bound-check style fixes first without a probability; consistent with MAT-ANCHOR (D-13). Cost: low. Risk: hand order is a hypothesis; validate with recall@k and effort@k on planted mutants (G-U2/G-U6). Source: R05 R10, which cites PatchScout (RankNet on handcrafted features; 92.70 % of 685 CVE patches located at acceptable workload, source-commit data) [int, not re-read].

**I-15 Root-cause grouping of induced changes.** Idea: if a function's only semantic delta is a callee that itself maps to a `material` row (or an inlined body that appears in an edited callee), attach the row to that root edit group as `induced`, ranked below the root; one canonical hunk replicated across N callers becomes one finding with N sites. Gain: large cut in changed-function noise from inlining (FM-1) and CRT/macro edits. Cost: medium (needs the callee map, available after L1). Risk: a real independent edit hidden in an `induced` row: show it as a collapsed child, never drop. Source: R05 F10 [int]; 1-to-n inlining analysis [S].

**I-16 Estimate evidence-class dependence from error co-occurrence, then join.** Idea: G-U7 currently measures B+B error vs tier-A error; add a direct statistic: on Tier R mutants and mismatched pairs, compute the co-failure rate of every pair of evidence classes (both wrong on the same pair) versus the product of their marginal error rates; join classes whose lift exceeds a preregistered bound by configuration. This is a direct test of the conditional-independence assumption that Dawid-Skene-type combination relies on (called "debatable" in the literature) and avoids naive-Bayes style overcounting. Gain: protects D-32 from correlated classes (for example E-BODY and E-DECOMP both derived from Ghidra decoding). Cost: low (harness). Risk: few errors in strong classes give wide intervals: report `insufficient-data` (already the 08 rule). Source: Dawid and Skene 1979 conditional-independence note https://ideas.repec.org/a/bla/jorssc/v28y1979i1p20-28.html and https://arxiv.org/pdf/1909.12325 [S, 2026-10-15].

**I-17 Calibration of rank outputs: per-pass empirical precision with intervals, then conformal sets for ambiguous buckets.** Idea: (1) keep the tier table; publish per-pass precision with cluster-bootstrap intervals and a monotone (isotonic-style) map from tier to a reported precision band, built only from Tier R lineages (Zadrozny and Elkan 2002 use isotonic regression for any ranking classifier); (2) for ambiguous buckets where the ladder abstains, emit a candidate set of partners sized by split-conformal calibration (nonconformity = rank of the true partner under the in-house bucket similarity) so that the true partner is in the set with a target coverage; (3) measure the review ranking with risk-coverage curves (selective classification: fix a target error, report achievable coverage). Gain: honest, validated uncertainty without introducing a probability the UI treats as truth (D-11 stays ordinal until the artifact passes). Cost: medium (harness plus a calibration table; conformal needs a held-out lineage split). Risk: conformal coverage is marginal and assumes exchangeability, which fails across compilers, toolsets and lineages (FM-11): calibrate per profile and per lineage group, state coverage as "on the calibration distribution", and report ECE only with fixed binning and intervals (ECE depends on bin choice). Temperature scaling (Guo et al. 2017) applies to neural logits and is not relevant to a rule ladder. Sources: https://scikit-learn.org/1.6/modules/generated/sklearn.calibration.CalibratedClassifierCV.html and https://www.cs.cornell.edu/courses/cs678/2007sp/ZadroznyElkan.pdf ; https://arxiv.org/abs/2107.07511v6 ; https://arxiv.org/abs/1705.08500 ; https://proceedings.mlr.press/v70/guo17a.html ; https://ojs.aaai.org/index.php/AAAI/article/view/9602 [all S, 2026-10-15].

**I-18 Toolchain-drift profile switch.** Idea: read linker/compiler fingerprints from both PE headers (linker version fields, debug directory build info, Rich-header-style metadata [U]) and the load-config feature set (CFG/XFG/GS flags); when they differ, record `toolchain-drift` in the result, expect a larger tier-B/C share, raise the cosmetic-proof burden (no COS-PSEUDO hiding) and show the banner in the UI. Gain: avoids mistaking a rebuild for a patch and sets the analyst's expectations (FM-11). Cost: low (header parse). Risk: fingerprints are spoofable or stripped; it is a hint only. Source: BinKit finding that build options change results https://arxiv.org/pdf/2011.10749 [S]; field set [U].

**I-19 Relational recall check against engine disagreement.** Idea: when an external engine (Ghidriff, BinDiff) pairs an endpoint differently from the ladder, run the edge-preservation count (I-12) for both candidate mappings and record which is more consistent as `contest.hint`, without changing `contested` (D-12) or choosing a winner. Gain: faster analyst resolution of contested rows. Cost: low. Risk: none to the contract (hint text only). Source: D-12; QBinDiff objective [F].

### 3.4 Suggested slice order [I]
1. I-07, I-16 (harness only, no behaviour change), 2. I-01, I-04, I-10 (ingest/propagation hygiene), 3. I-02, I-03, I-05 (twin keys, behind pass flags), 4. I-06, I-08, I-12 (group and veto rules), 5. I-13, I-14, I-15 (ranking), 6. I-09, I-11, I-17 (larger, after Tier R data exist), I-18 and I-19 any time.

## 4. What not to do

1. Do not average, sum or multiply native scores across engines (Ghidriff ratio is a text-diff statistic, BinDiff confidence a step prior, Diaphora ratio a text similarity); the spec already forbids it (D-11), and correlated engines make a naive-Bayes product overcount (R05 s3 rationale a).
2. Do not use RRF, Borda or any rank fusion to accept or label a match; only to order rows inside an already decided bucket (I-13).
3. Do not run whole-binary quadratic assignment, belief propagation or a dense Hungarian in pure Python; QBinDiff's README itself advises against more than about 10k functions without sparsification [F], and our images reach 60k+ (L-01). Restrict optimisation to blocked residual buckets (D-25).
4. Do not put neural embeddings (Asm2Vec, jTrans, DeepBinDiff) on the default path: they answer retrieval/similarity, not "what changed", need training or GPU and disassembly stacks, assume stripped same-ISA inputs, and a raw-bytes baseline is reported competitive on Windows data (REFuSe-Bench, https://arxiv.org/pdf/2410.22677 [S]). Optional experiments only, never suppress rows.
5. Do not trust address order, RVA proximity, function size or instruction count as primary evidence under `/GL`/PGO images (FM-2); use order only as a guarded tie-break (I-08).
6. Do not force a 1:1 pairing on leftovers, do not cross-multiply N:M, do not report an inlined or folded function as "removed".
7. Do not treat Diaphora's long heuristic list or its minimum ratios as calibrated; copying thresholds imports IDA-export tuning (R04 s8) and AGPL code is forbidden (D-24).
8. Do not claim conformal coverage or calibrated probabilities across toolchains or lineages without per-profile calibration; do not show a number before the SPEC-28 artifact passes (D-11).
9. Do not hide `COS-PSEUDO` or any decompiler-relative verdict on the strength of a single channel, and do not let tier-B pairs corroborate anything until two components and two evidence classes agree (D-32).
10. Do not take Microsoft-behaviour claims from this note as facts for UI text (see section 0); several are search-summary level.

## 5. Open questions

1. Does MSVC (not LLVM) emit PGO cold code as chained `.pdata` fragments, as separate RUNTIME_FUNCTIONs with `$cold`-style names, or both? Determines whether I-01 is inert. Needs a matrix build with `/GL /LTCG /GENPROFILE` then `/USEPROFILE` and an `.pdata` dump.
2. How large is the matched-by-twin-key share (I-02/I-03) on real Windows feature-update pairs, and does it come at an acceptable precision cost per the G-U3 table?
3. What is the empirical Kendall tau of tier-A anchors between consecutive Windows builds with and without PGO, i.e. is the adaptive order tie-break (I-08) ever enabled on kernel images?
4. Which evidence-class pairs show correlated errors (I-16)? E-BODY vs E-DECOMP and E-NAME vs E-CALL (names inform propagation) are the first suspects.
5. Can a conformal set (I-17) be sized small enough in ambiguous buckets to be useful, given that exchangeability fails across toolchains? Needs per-profile calibration data from Tier R across clang-cl, mingw and MSVC.
6. Are there published accuracy tables for Karamitas (xul.dll vs Diaphora), BinSlayer, QBinDiff on Windows PE patch pairs? None were readable here; a human should read the evaluation sections before preregistering recall/precision targets (R04 s10).
7. Which of the secondary claims here (CFG noise in Windows 10 builds, large-binary mis-matches) hold on our corpus? They are single-source blog/tutorial statements.
8. Is an XFG prototype hash a reliable free candidate filter between unmatched functions, or does it change with unrelated type edits (R04 s6 [U])?
9. Licence and NOTICE review for any BinDiff-derived relaxed MD variant (U-01).
10. Which of Diaphora's 50 rules have positive marginal contribution on Windows PE pairs (I-07)? The "Seems not to find anything?" comments are on IDA corpora of unknown composition.
