# Failed backup publication must remain ineligible

Source: `9c468bc75077484c1780305d7cc927b30fd0bc8b`, PR #151 [review 5734146359](https://github.com/djshellshoxxx/patchtrace/pull/151#pullrequestreview-5734146359).

The finding is confirmed by a real SQLite flow, not just a leftover filename. The post-link seam deletes rows from the new copy using SQLite, preserving an `integrity_check=ok` database, project identity, snapshot SHA and required tables. The first public retention attempt returns 0 and preserves 40 live entries. After clearing process verdicts, discovery adopts the failed publication; the next actual retention call deletes eight entries absent from that copy. History initially blocks pruning for the session, but a real close/reopen/save deletes six prior history rows absent from its failed copy. With an earlier valid backup present, its bytes survive and remain recovery evidence, although the newer failed copy is selected on the baseline. Matching the current snapshot cannot repair the retention example because that SHA was unchanged.

The repair uses the existing unique staging filename as an admission guard. Final-name discovery precedes the staging-name scan; a matching `<final stem>-*.sqlite3.part` excludes the final name. The final byte revalidation now happens before owned-stage cleanup. A post-link failure retains its stage and diagnostic bytes, raises `BackupError`, and cannot be adopted on another call or after restart. Nothing unlinks or renames a final path. Earlier completed timestamps remain eligible; replacement destinations and replacement staging files remain untouched. An unchanged verified copy with a staging cleanup failure is conservatively refused by later discovery while its stage remains. Successful publication retains the existing fresh-byte reuse rule.

Final regressions copied byte-for-byte to a detached exact baseline: **7 failed, 1 passed in 1.44 s**. The first red run also gave 7 failures / 1 pass; the final file strengthens the replacement control to a valid, same-project SQLite replacement. Repaired verification: **60 passed in 5.68 s** across publication admission, reuse filtering, byte integrity, stat-API differences, prune backups, retention and history bounds. Whole-repository Ruff and whitespace checks passed. No existing test expectation or hash/integrity check was weakened.

The adjacent archive contains logs, source-bound manifest, the reproduction, and failed/earlier SQLite copies. The initial history probe reduced the history limit during sample creation, which created an earlier valid backup before the failure hook; its setup error is retained. The corrected probe lowers the limit after fixture creation and reproduces the later deletion described above.

Independent frozen-source review and central integration are pending. This is local Linux SQLite evidence, not native Windows, full-suite, performance, arbitrary same-user mutation resistance or power-loss acceptance. Legacy backup names without a matching unique stage retain the previous adoption rules; the change does not invent historical publication verdicts for them.

Independent review of candidate `536aebc` found a blocking error path: `Path.glob` suppresses directory scan errors, so an unreadable pending-stage scan could appear empty and re-admit the failed copy. Three independent error controls reproduced that; an actual other-thread pending-publication control passed. The follow-up uses explicit `os.scandir` for both enumerations and refuses all candidates on open, iteration or entry-read failure. Author regressions reproduce second-scan open and mid-iteration failures (2 failed / 1 passed before repair); the repaired related selection gives **63 passed in 5.57 s**, with whole Ruff/diff clean. The additional evidence and original independent blocker receipt are retained in `backup-publication-admission-scan-20261102.tar.gz`. A new frozen-source independent review is required; the earlier 60-pass result did not cover this defect.
