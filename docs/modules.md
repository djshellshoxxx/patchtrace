### [PIL-B1:rules] rule-table notes (decisions beyond plan s7)
- Scope is 22 K rules, not the card's 20. Audit C had already added `R-FORMAT-STRING` and `R-OFF-BY-ONE` (families `format-string`, `off-by-one`) to `lexicon.py` and `hypotheses.py` with their tests, so the card's additive K edits are present and none were made here. CWE-193 stays in its own family: moving it under `bounds` would change the K rules digest and break `test_intel_hypotheses.py`. The two rows the plan's draft table lacks were authored from the K rule text (one required change each).
- Rows: the first change of a row is its only required one. MEMORY-WRITE, MEMORY-READ, BOUNDS: guard-added, size-recomputed, checked-arithmetic; INTEGER: overflow-check, range-check; LIFETIME: ref-release, state-check; INFO, UNINIT: zeroed; INPUT: validation-added; NULL-DEREF, POINTER, TYPE: check-or-probe; the nine API-level rules: api-level; FORMAT-STRING: constant-format; OFF-BY-ONE: bound-adjusted. `teach_id` is `pilot.change.<id>`. Every rule lists the conflict leaves `cf:cosmetic` and `cf:unchanged`. No capa leaf is shipped (plan s4: the namespace map is empty in v1). `call:` leaves appear only where the K rule has `api_hints`. INPUT also accepts B1 `BND`, so B3's CWE-1284 -> (VAL, BND) entry is covered (`test_cwe_detector_map_consistent_with_rules`).
- Leaf semantics. `b1:<DETECTOR>@<min>`: a signal of that detector with confidence at least `<min>`; a floor above what the detector can report is rejected (BND, OVF, SIZE, SCRUB report moderate, VAL and ERR weak, INT weak or moderate; `strong` is unreachable). `cf:<class>`: one of the nine SPEC-31 semantic classes. `call:added|removed@api_hints`: a call whose API name, by CAP's `api_key` (lower case, no module prefix, trailing A or W folded when 4 or more characters remain), is one of the K rule's `api_hints`. `capa:ns=<prefix>`: a capability at or below the namespace. `cf:cosmetic|unchanged`: conflict leaves. `str:*` is recognised and refused everywhere: strings and DiE flags are context only and can neither meet nor contradict a change.
- Evaluation. Only `shape` evidence can meet a change and only `conflict` evidence matches a conflict leaf. A change is `met` when any leaf matches (every matching observation id is kept); else `contradicted` when conflict evidence exists (its ids); else `not-observed` only when every channel its leaves read (code, calls, capa) is `available`; otherwise `unknown` (partial, not-run, unsupported, failed, stale, or missing from the mapping). A conflict next to a met change leaves it `met`; PIL-B2 reads `conflict_ids` to force `contested`.
- Digest. `pilot_rules_digest()` is `domain_id('pilot-rules', 1, {version, vocabulary, rules})`: rules sorted by id and revision, leaves sorted inside a change, change order kept. Bump `PILOT_RULES_VERSION` when evaluation semantics change. The domain is not in A1's `keys.DOMAINS` (its test pins six) and nothing needs it there.
- Caller contract: `Evidence(obs_id, kind, role, level, subject)`. A1's `Observation` has no field for the B1 signal confidence (`level`) or for the API name or capability namespace (`subject`), so PIL-A3 and PIL-B2 must agree on the carrier. The table never copies K's `api_hints`; the caller passes the hypothesis's own.

### [PIL-A2:advisory-sources] decisions beyond plan s7 and s9
- Gate precedence, strongest statement first: conflict (any contradiction, also one on products mapped to neither side, as the table says; or a side that resolves contradictory), then not-applicable (older not affected, newer still affected, or both sides fixed or not affected), then unverified, then applies. A contradiction is never settled by suppressing leads. The analyst's `--assume-applies` only turns `unverified` into `asserted`; a conflict or not-applicable gate stays and the context says the assumption was not used.
- Window: the imported CSAF documents are a partial list, so they can establish `yes` (the threshold is `PilotConfig.confounded_min_cves`) but never `no`; fewer CVEs leave the window `unknown` (no cap, the caption says so). `no` needs a complete KB window. More than 1,024 CVEs in a window is `PT-PILOT-LIMIT`, not a cut list.
- Ledger shapes: `adv:cwe-stated` (verification `advisory-claim`, basis explicit field or CWE id in the text) and `adv:cwe-derived` (`rule-hypothesis`, vocabulary match), role `context`, origin `D_vendor_text`, class `E-TEXT`, anchor `cwe:CWE-n`; `ref.sha256` only when exactly one current document holds the pointer. Weak matches, KEV `cwes` and advisory phrases produce no entry here (the `Kev` record has no `cwes` field).
- A record without product data has both sides unmapped (gate `unverified`, or `asserted` on assumption); a CWE is the explicit field only when the record names exactly one, several stay claims in a note, a disagreement between providers is a limitation line, never a vote.
- Ports: KEV uses A1's `KevSource`; the KB track fills the new `KbWindowSource` (declared in `window.py`, FAB or the KB track may move it into `ports.py`).

### [PIL-B2:engine] decisions beyond plan s7 (read with the module table above)
- Contexts. The code-only context (`cve` None, gate `none`) is always present, then one context per CVE sorted by id (the dock's "No advisory (code evidence only)" row); a `not-applicable` CVE keeps its context with zero counts and no leads. A context's `counts` are the true totals; `leads` hold what P-04 keeps (500 leads, 200 queue rows); `queue_count` is the number of queue rows left out, over all contexts; `limits_hit` slugs: `leads-cut`, `queue-cut`, `observations-cut`. `status` is `partial` exactly when a limitation line exists (a `failed` or `stale` channel, a CVE without a stored report or a K rule revision without a PIL row, any cut) and `abstained` when the pairing channel is unusable or there is no candidate. An unusable channel (not-run, unsupported, failed, stale) contributes no observation: unknown, never a negative vote.
- Tier, as built. `eligible` (could be moderate) needs: every required change met; each of them met by at least one observation that is not `label-only` (s4 "label-only calls support at most tentative"); two independent components; for the 14 rows without a B1 detector two independent origins among the code observations alone (s7 "stay tentative unless two components agree", read as: the advisory does not count, a Ghidra label plus a PE import does; an owner decision if the plan meant the advisory to count). Caps (a cap is recorded only when it bites): confounded window without locality, toolchain-changed or packed with no material typed support, unverified gate; a conflicting gate, a contested pairing or a named proof turn a still-moderate lead into `contested` (review). `lexical_moderate=false` holds a lexical lead at partial without a cap slug (the contract has none). `tentative` = a change of the best hypothesis met, or locality plus change evidence; `unexplained` = changed, no fit.
- Components are the A1 connected components over the origins of the observations that meet a change of the best hypothesis plus the advisory's entries, and only when a change is met (the advisory is not a witness for a function that shows none of its expected changes); locality (`loc:names`, role `local`, origin `D_symbols`, one entry per lead with nav) never counts. With several origins on one observation the calculus is not monotone under removal (a bridge); no adapter emits one.
- B1 confidence is the detector's default (`fusion.B1_LEVEL`, pinned to `enrichment.signals.DETECTORS`; `INT` is read as `weak`), because the observation does not carry it. The code channels compare one function with one function: for a one-sided or group candidate every change is `unknown`, never "not seen".
- Locality: `enrichment.cve.name_terms` of both function names against the advisory's `component` anchors, with the tokens of its `module` and `feature` anchors removed, per phrase (tokens of two phrases never combine), at least `locality_min_tokens` (2); Ghidra default names (`FUN_`, `sub_`, `thunk_`) never count. Quoted advisory strings are not joined: T's `value_hash` is case exact and no source supplies the string references of an IR function.
- Observation lists of a lead: `counter` (conflict or counter role), `alternative` (noise classes, nuisance flags, DiE), `unknown` (quality flags, capa without a function), `support` (the rest, the advisory's entries when a change is met, the locality); at most 256 (P-02): alternatives, then unknowns, then plain context go first; evidence behind an expected change, the advisory's entries and the locality stay.
- Order. Keys are tuples of ints (`ranking.py`); ties are the groups of equal keys; inside a tie the order is the candidate key (no attention/1 rank source exists), never the RVA. A contested pairing sorts last; `constant` takes the compare-context position of the SPEC-31 severity list.
- Speed: a rule is evaluated once per evidence pattern (kind, role, B1 level, whether a call names an API hint) and shared by every candidate that shows it; `ExpectedChange` records exist only for the kept leads. 5,000 pairs x 8 CVEs (two hypotheses each, every pair with four observations) take about 2.2 s of CPU in the container.
- Not built here: the store, report and CLI (PIL-C1), the read model and dock (PIL-C2), anchor publication to an `AnchorSink`, the KB window (the contexts carry the CSAF-derived count), the quoted-string locality.
