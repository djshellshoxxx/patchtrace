# Immediate next-build GUI and preliminary PE inspection requirements (SPEC-26 proposal)

Status: IN PROGRESS. Code fix in this PR: cross-function next/previous diff navigation and provenance tooltips for the code panes/hunk controls. Other requirements below are NOT implemented by this PR yet and must not be advertised as shipped. Priority P0 for next release. Coordinate with SPEC-12–25 planning and current Phase 3; do not change analysis results.

## Acceptance requirement A: universal informative hover tips

Every functional action, menu item, button, checkbox, radio, combobox, spinbox, slider, filter, editable field, list, clickable result and code pane across MainWindow, dialogs, Setup, acquisition, interpretation, export, secondary comparisons and upcoming preview has a meaningful tooltip. The sole exceptions are the **New** and **Open** action/buttons. Each tooltip explains: WHAT the control does, WHY it exists, WHAT changes when used, SOURCE and scope of displayed data (if applicable), availability and limitations. A field explains accepted type/example. A control disabled for absent selection states prerequisite. Tooltips must be readable without truncated text (use escaped plain or sanctioned rich text), accessible for keyboard and screen-reader users (accessible description/status tips), and must never interpolate raw unescaped binary names/model output. Create a declarative tooltip registry keyed by semantic control ID, not window position or visible string. For static controls assert an exact registry entry; for dynamic items use a sanctioned parameterized source-safe template. GUI tests enumerate all active focusable widgets and actions and fail if tooltip absent/empty/boilerplate, with explicit two-control exception. Test each dialog, tooltip on disabled elements, and both themes/scaling.

Required code pane description: decompiled code is C-like decompiler output produced by Ghidra via Ghidriff, **not** original source; assembly is only real instructions when upstream retained them; metadata comes from saved normalized/raw analysis; line gaps are PatchTrace-only display alignment; no textual display implies bytes were extracted from the selected function. For new raw file representations, show whether representation is *whole file*, *file range*, or a *function RVA range*, and whether bytes are original on disk or transformed.

## Acceptance B: representations (Decompiled, Assembly, Metadata, Hex, Binary, Base64)

Extend the existing mode selector using representation providers, not conditional spaghetti. Raw byte view must read verified project-owned immutable artifact bytes with independent file hashes; never encode decompiled text and mislabel it as binary representation. For **whole-file raw views** add explicit scope selector and bounded paging (offset, length, goto RVA/file offset) with hex address gutters. For **matched function bytes** map function virtual addresses via PE section RVA-to-file offsets, honoring virtual-only gaps, ranges, non-contiguous blocks, overlapping sections, relocations and file overlays; show unavailable when function extent cannot be safely determined; never substitute a guessed range. Hex = offset + hexadecimal byte columns + optional ASCII; Binary = 8-bit byte sequences with offsets; Base64 = RFC 4648 encoding of the exact selected bytes with offset/length/hash caption. Alignment for raw bytes is byte/range alignment and must not re-use text SequenceMatcher hunks. Limit memory/CPU and cap render sizes; asynchronous paged reads. Provide explicit encoding/scope markers, copy exact displayed content with attribution, and disable code-line evidence navigation when viewing raw bytes. Tests include nulls, high bit, PE section unmapped gaps, offset overflow, huge files, range clipping, base64 padding, and SHA mismatch. Metadata remains metadata and does not mutate binary bytes.

## Acceptance C: diff navigation

Next/Previous traverse actual changed hunks, then subsequent/previous visible functions after end/start (no silent no-op for a one-hunk function). Respect search/category/review filters and selected function, stale/replaced runs; scroll, highlight, hunk label and status agree. At edges provide visible 'No further changed functions' feedback; do not wrap invisibly. If current displayed mode has no text hunks, explain reason. Tests: 0/1/2 hunks, 1/2/3 visible functions, skipped unchanged, empty/filtered results, mouse/Alt keys, selection changes, switch mode, multi-function split/merge, line map, clipboard and rendering.

## Acceptance D: instant lightweight file-side comparison upon Run comparison

Immediately after Run Comparison, and before expensive backend startup, start a separate low-cost read-only metadata inspection worker using project-owned immutable input paths. Show side-by-side OLD/NEW on a dock/tab **Preliminary file comparison** while external Ghidriff and optional other engines continue. **Do not block analysis on optional metadata extraction failures.** Persist a versioned overview keyed by immutable artifact SHA and inspection implementation/version. Field-by-field changed/unchanged/unavailable indicators with reason and provenance. Avoid modifying project state from worker thread. Previous complete analysis remains intact during a running job and preview failures.

Minimum fields: original/display filename, selected orientation, file size bytes/delta, SHA-256 plus SHA-1 optionally, MIME/header magic, detected PE type (EXE/DLL/SYS heuristics), PE machine/architecture/subsystem, COFF timestamp (untrusted as filesystem creation date), filesystem create/modify times where reliably available, PE optional-header entrypoint RVA/VA, image base, alignment, section count and per-section names/raw/virtual sizes, RVA and flags, imports/exports counts/names (bounded), relocation/TLS/exception/debug/resources/security directories, imported DLL list and notable API changes, version-info strings, manifest availability, PDB path/build ID where safely parsed, presence of overlay and suspicious/unmapped regions, section entropy and well-known packer heuristics with uncertainty, embedded certificate signer/chain/timestamp and **Windows Authenticode trust verification** via WinVerifyTrust with offline/no-revocation default clearly labelled (not 'fully valid' without revocation). Display signing time only when trustworthy timestamp evidence exists. Certificate-table checksums and strong/weak digests clearly separated. Distinguish 'unknown' from 'unsigned' and 'invalid'. COFF timestamp can be forged; never infer file creation from it. **Entry point registers are runtime state and not stored in a PE header:** report architecture, entrypoint address and expected loader context only; actual register values require debugging. Compression cannot be reliably deduced from entropy alone; display probable packer/algorithm only with evidence and a confidence label.

Recommended pure modules: pe_overview/models.py, reader.py, headers.py, sections.py, metadata.py, signature.py (Windows-specific adapter), entropy.py, compare.py and ui/preflight.py. Prefer stdlib for hashes/stat and well-maintained bounded PE parser (pefile or lief with pinned versions) under separate fault boundaries; WinVerifyTrust for Windows, with explicit offline/revocation behavior. No shell calls, no loading DLLs, no executing target, no automatic trust/network downloads. Budget and graceful degradation documented. Tests: unsigned, invalid, valid timestamped, trusted revocation unknown, corrupt/short/truncated PE, weird headers, hostile RVA, packed/high-entropy, overlay, PE32 unsupported input, input swapped, same hash, path spaces/Unicode, large file, file mutated after copy, cancel mid-inspection, missing Windows API.

UX progress: 'File inspection' independent from 'Ghidriff analysis', show each stage and failures; preview visible while comparison runs and still available after. When preliminary data available, switch to preview only if user has not manually selected another tab. Provide provenance and interpretation tooltips per field. Present no estimated signature validity from mere presence of a certificate.

## Acceptance E: multi-engine incremental results

Existing Phase 3 BinDiff and rz-diff remain opt-in. Each result emitted with provider/version/config/artifact identity and matching algorithm in a separate panel, then reconciled with Ghidriff once relevant results complete; do not treat uncalibrated similarity percentages as equal. Allow preliminary PE differences before any expensive diff engine. BinDiff can add structural flowgraph, callgraph, basic-block match evidence and alternative correspondences; rz-diff adds bytes/sections/imports/symbols/functions/graphs comparisons, with cheap modes before expensive ones. Independent failures cannot hide other results. CPU/RAM concurrency cap and artifact/analysis reuse when possible.

## Alpha preview slice: recorded artifact overview (PR #19)

The first GUI slice provides a nonmodal **File overview** action. It shows old/new filenames, byte sizes, size delta, recorded SHA-256 hashes, same/different hash relation, and the validated stored PE/x86-64 input classification. It is available on sample or real projects without a configured analysis backend, and automatically opens before a configured native comparison starts. Values come from the project snapshot recorded during initial ingestion. There is no new disk reading, PE disassembly, entrypoint extraction, signature trust check, or implicit network operation. Plain-text cells isolate untrusted filenames. This slice is a UI alpha, not acceptance of requirements B, D's full PE detail, or E. All detailed fields, async inspection, whole-file paging, verifiable signatures, and broader tooltips remain open.

## Alpha shared byte seam (artifact_bytes.py)

All raw-byte consumers (PE inspection, Hex/Binary/Base64 views) read through `patchtrace.artifact_bytes.VerifiedArtifactReader`. It opens the project-owned copy via `safe_path`, hashes it on the same handle it later reads from, rejects size/hash mismatch, detects post-verification changes (size/mtime on the open handle), caps a single read at 16 MiB and either clips or rejects ranges past end of file. Failures raise `ArtifactBytesError` with stable codes (`path_invalid`, `unreadable`, `hash_mismatch`, `size_mismatch`, `artifact_changed`, `range_invalid`, `read_too_large`, `closed`, `cancelled`). Callers display the code and never substitute guessed bytes.

## Alpha tooltip registry

Landed (requirement A, first slice): `src/patchtrace/tooltips.py` holds a declarative registry of `TooltipEntry` records (what, why, effect, source, availability) keyed by semantic IDs such as `action.run_comparison`, `viewer.older_code` and `setup.ghidra_dir`. Static controls use `tooltip(id)`; dynamic items (recent project paths, detector IDs) use `template(id, **values)`, which strips control characters, caps values at 200 characters and escapes them. `apply_tooltip` sets tooltip, what's-this, status tip (actions), accessible description (widgets) and an empty object name. Every MainWindow action and widget, NewProjectDialog, AcquisitionDialog, SetupDialog (both tabs and profiles), ContextDialog, CorrectMatchDialog, ExportDialog, the file overview dialog, text dialogs and Yes/No confirmation buttons use it. New and Open are the only exempt actions (`EXEMPT_IDS`). The code pane entries state the required provenance wording. `tests/test_tooltips.py` enumerates actions and focusable widgets in each window and dialog and fails on missing, short or non-registry tooltips.

Second slice (2026-10-28): the swap-orientation confirmation is an instance box whose Yes/No buttons use `confirm.yes` and `confirm.no`, and the critical error box's OK button uses `error.dismiss`. `tests/test_tooltips.py` covers both.

Still open: per-item tooltips for list and table rows still use the earlier ad hoc escaped text (`plain_tip`) rather than registry templates; tooltips for the Hex, Binary and Base64 representations and the whole file, file range and function RVA range labelling (requirement B) wait for those features; both-theme and display-scaling tests are not yet written; New and Open are intentionally untouched.

## Alpha integration (artifact_inspection.py, raw_view.py, ui_inspection.py)

**Landed:** The File overview dialog keeps the recorded-metadata table and adds a field-by-field **PE comparison** (headers, sections, imports, exports, overlay, certificate-table presence) with changed/unchanged/unavailable status and provenance per field. Inspection runs on its own `InspectionThread`, independent of the Ghidriff job worker, re-verifies each artifact copy's SHA-256 and never mutates the project. It starts when the dialog opens (including the automatic open on Run comparison) or when a raw mode is selected, and its result is keyed by project root, project ID and both artifact hashes, so Swap orientation or switching projects invalidates it. The viewer mode selector adds **Hex**, **Binary** and **Base64** of original on-disk bytes, with a scope selector (Whole file / From function entry), a page spinner (4,096 bytes per page) and a hexadecimal go-to file offset field. Lines containing differing bytes at equal logical offsets are highlighted (Hex/Binary only). Next/Previous diff explain that raw views have no text hunks. Copy places the displayed page with artifact, scope, page and SHA-256 provenance on the clipboard.

**Deliberate limits:** Ghidriff records carry an entry address but no verified contiguous function body, so "From function entry" pages forward from the mapped entry offset and states that the function extent is not determined; unmappable/virtual-only/ambiguous entries show unavailable. Split/merge relationships use the first function per side for entry scope (stated in the header line). Page reads (at most 4 KiB) run on the GUI thread; hashing and PE parsing run off-thread. The PE comparison is not persisted per artifact hash yet. The Authenticode probe (`pe_overview/authenticode.py`: embedded signature only, WinVerifyTrust with no revocation and cache-only URL retrieval) runs on each hash-verified copy and appears as a row whose wording never claims full validity; it reports "not checked on this platform" off Windows. It opens the file by path after the hash check, which is acceptable for immutable project copies; signed/trusted/revoked samples still need native Windows acceptance. Section entropy, packer hints and parser warnings are in `PeOverview` but only partially surfaced.

Migration M3 (GUI plan section 8, slice F9): the File overview dialog becomes a `files` dock, and `ui.py` loses about 65 lines. Until F9 it is a recorded exception to "one main window" (GUI plan open question 7).
