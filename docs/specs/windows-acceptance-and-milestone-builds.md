# Windows acceptance and milestone builds

## Desktop archive preflight amendment (2026-11-05)

`tools/check_windows_package.py ARCHIVE --sha256 DIGEST --commit SHA --label LABEL`
checks a Windows **desktop** portable ZIP against an independently obtained expected
SHA-256 and source identity. It never extracts or executes archive contents, downloads
dependencies, or marks Windows acceptance passed. Its JSON receipt records archive
size/digest, manifest identity and file count; Windows smoke, native and manual gates
remain `not-run`. A matching digest establishes equality to the supplied digest, not
publisher authenticity.

Before opening ZIP members, bound archive size to 2 GiB, central directory to 16 MiB
and entries to 50,000; refuse ZIP64 and split archives explicitly. Accept only stored
and DEFLATE compression, as emitted by the current builder. Bound total declared
expanded bytes to 4 GiB and each metadata JSON to 4 MiB. Reject encrypted members,
non-file/non-directory Unix types, duplicate/casefold/NFC-colliding names, unsafe
Windows path components (255 UTF-16 code units maximum), NUL-truncated ZIP names,
and file/directory-prefix conflicts. Require the single
`PatchTrace/` root, a nonempty `PatchTrace.exe`, replaceable Qt6Core DLL and Windows
platform plugin, a Python DLL, Python and Qt LGPL notices, `dependency-versions.json`
and `file-inventory.json`. Runtime files must occupy the current PyInstaller layout:
`_internal/python3*.dll`, `_internal/PySide6/Qt6Core.dll` and
`_internal/PySide6/plugins/platforms/qwindows.dll`. Parse JSON strictly. The dependency manifest must identify
the exact expected PatchTrace label and 40-character lowercase source commit, plus
nonempty Python/PySide6 versions. Inventory must equal the archive's files except
the inventory itself (the current builder emits its inventory before writing it).
Archive contents and inventory names use identical path validation. Check the opened
archive's metadata for mutation after hashing and metadata inspection. Do not claim
protection against a hostile writer that can alter and restore all observed metadata.

This is a structural preflight: executable resource identity remains
`check_windows_exe.py`, decompression/CRC of every payload and frozen execution remain
the clean Windows extraction/smoke. The full offline bundle uses its existing backend
manifest validator and disconnected qualification; this preflight does not qualify it.

## 1. Milestone build policy

### 1.1 What publishes today

From `.github/workflows/qa-windows.yml`:

| Trigger | Jobs that run | Publishes a GitHub prerelease? |
|---|---|---|
| `push` to `main` | `qa` (ubuntu-latest, windows-latest), `qt-gate` (Linux and Windows), `windows-validate`, `linux-package`, `linux-smoke` (22.04, 24.04), `release-gate`, `release` | Only if `qa`, `qt-gate`, `windows-validate` and `linux-smoke` succeed and the release gate says so (every third counted merge, see the release gate paragraph below). | `push` of a tag matching `v*` | same jobs | Yes. The tag name is used as the release tag |
| `pull_request`, `workflow_dispatch` | QA jobs only | No |

- `live-backend.yml` (native Ghidriff matrix) never publishes. It is a gate for the same SHA.
- The `release` job has no `paths` filter; the release gate (paragraph below) limits publication to every third counted merge, and a docs-only merge that carries a skip marker neither runs the workflow nor counts.
- `linux-package` requires both `qa` and `qt-gate`. `release` directly requires `qa`, `qt-gate`, `windows-validate`, `linux-smoke` and `release-gate`; its condition retains GitHub's implicit success check. A tag or `publish=true` cannot bypass a failed, cancelled or skipped acceptance gate. The cadence gate's fail-open policy does not bypass acceptance checks.
- Each `qa` matrix leg records `job.status` after its final acceptance step (including Windows portable and installer acceptance), immediately before the always-run evidence artifact upload. Release notes read these per-leg results and use the aggregate QA result only when a status file is missing.
- `run_number` counts every run of the workflow, including PR and failed runs. Observed tags therefore have gaps (beta.118, .120, .127, .129, .131).
- Release notes are generated by `tools/milestone_notes.py` with the selected tag and ref kind; the fixed fallback preamble does not label tagged builds as beta. `target_commitish` is `github.sha`.
- Uploaded release assets (`release/*`): `PatchTrace-0.1.0-windows-x64.zip`, `PatchTrace-0.1.0-windows-x64.zip.sha256`, `PatchTrace-0.1.0-linux-x86_64.tar.gz`, `PatchTrace-0.1.0-linux-x86_64.tar.gz.sha256`. The version `0.1.0` is hard-coded in `pyproject.toml`, both build scripts and the workflow, so the tag is not in the filenames.
- Known failure mode: publishing returns HTTP 403 `Resource not accessible by integration` when the head commit adds or changes `.github/workflows/*` (see `docs/plans/phase-c-multi-engine-plan.md`, handoff B1). The build is green but no release exists. The ZIP and tarball remain as Actions artifacts `PatchTrace-windows-x64` and `PatchTrace-linux-x86_64`. Report such a run as "build green, publish failed", never as a release.

**Release gate (slice RG, `tools/release_gate.py`).** A push-only `release-gate` job decides whether this push publishes: `release` needs it and runs only for a `v*` tag or when the gate prints `publish=true`. The gate counts the first-parent commits on `main` after the commit (`target_commitish`) of the latest published, non-draft prerelease whose tag starts with `v0.1.0-beta.`, the head included, and publishes at the third. It also publishes for a head message containing `[release]`, for a tag, when no such prerelease exists or the latest one is not on the head's first-parent history, and whenever the gate itself fails (fail open: the reason is printed, and the count and the reason go into the release notes). A commit whose whole message, subject and body alike, contains `[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]` or `[actions skip]` is not counted, because GitHub runs no workflow for it and no build exists; the head always counts, because this run exists. Consequences: `qa`, the packages and the smoke jobs still run on every push that is not skipped; a squash body that quotes a marker on any line skips the whole push run (PR #48 was skipped that way), so do not write the literal markers in commit messages or PR bodies unless that is the intent, and `[release]` belongs to the owner and instance A; two runs in flight at once both read the release list before either publishes, so an extra prerelease is possible; a `workflow_dispatch` run no longer publishes even from a `v*` tag ref, because the gate job is push-only.

### 1.4 Offline verifier archive safety amendment (2026-11-18 UTC)

`tools/verify_release.py` inspects archive metadata and bounded metadata members;
it never extracts archives or executes their contents. Required ZIP members must
be regular files: an absent Unix type field is compatible with conventional ZIP
writers, but explicit directory, symlink, FIFO, device or socket kinds cannot
stand in for a required file. Unsupported special members anywhere in ZIP or tar
are archive-content failures.

Member identities normalize dot and redundant separator aliases, treating both
slash spellings as separators; Windows ZIP identities also normalize Unicode to
NFC and fold case. Colliding member identities fail. Windows ZIP member names
and link targets reject components with trailing dots or spaces, reserved device
names (case-insensitive, including extensions and the superscript COM/LPT forms),
colon/alternate streams, Win32 forbidden characters or controls, invalid Unicode,
and more than 255 UTF-16 code units. Dot and parent components in link targets
retain their normal relative-path meaning and must still resolve inside the
archive. ZIP names truncated at NUL by the ZIP reader fail rather than validating
only their visible prefix. A reader's ordinary backslash-to-slash normalization
is not NUL truncation and remains a valid separator alias; inspect the original
name for NUL rather than treating every reader spelling change as corruption.
These Windows rules do not restrict Linux tar names.
No member may be located below a symbolic or hard link,
irrespective of archive order. Link targets are resolved component by component
against the complete declared link map, so a link followed by `..` cannot hide
an escape through lexical normalization. Symbolic targets start at their
member's parent; hard-link targets start at archive root. Absolute targets,
root escapes, targets over 4,096 bytes and chains exceeding 64 link expansions
fail. Ordinary relative links that stay inside the archive remain supported;
their target need not be present for this structural check. This is not evidence
of successful extraction or execution on Windows or Linux.
