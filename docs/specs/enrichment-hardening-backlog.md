## H1. Enrichment row retention (storage cap deadlock) , tier M

Current: `EnrichmentStore.publish` upserts by id (`storage.py:122-149`) and nothing in `src/` ever issues `DELETE FROM enrichment_entries` (grep verified). Row ids are `kind:<ranking stage id>` / `wil:<wil stage id>` / `contextual:<ctx stage id>` (`pipeline.py:300-314`), so each project change that alters the input digest, each non-default profile and each snapshot set adds a full new generation. At `used + size > MAX_TOTAL` (128 MiB, `storage.py:134-138`) publish raises recoverable `PT-ENRICH-LIMIT` forever; the only remedy today is deleting the project.
Target:
- **Generation** = the pipeline row `pipeline:<rid>` plus the rows its body references: `signals:<rid>`, `ranking:<rid>`, `wil:<stage_ids.wil>`, `contextual:<stage_ids.contextual>` (when present). `wil`/`contextual` rows may be shared by several generations: reference counted by scanning retained pipeline bodies.
- **Classes**: *current* (guard equals the live guard and row `stale=0`), *stale* (anything else). `secondary-matches` is imported evidence that cannot be recomputed offline: **never evicted by retention**, only counted toward the cap (newest 8 per `run_id` kept; older ones are removed only by an explicit user action, out of scope). Unknown kinds and `read_only` (newer `extension_version`) stores: no deletion, ever.
- **Defaults**: keep at most `KEEP_CURRENT = 8` current generations (newest `created` first; distinct profiles) and `KEEP_STALE = 2` stale generations per `config_digest` (provenance of "what the analyst saw before the rebuild", consistent with SPEC-07 §3 "history is kept"). Everything else is deleted.
- **When**: (a) after `pipeline.publish` writes the `pipeline` row, one call `store.apply_retention(current_guard, protect=ids_just_written)` in a single `BEGIN IMMEDIATE` transaction; (b) **cap fallback** before the first `put` of a publish: `store.make_room(estimated_bytes, protect)`; it deletes in order stale generations (oldest first), then current generations beyond the newest 1 per `config_digest`, never touching `protect` or the live default-profile generation; only if still over the cap does it raise the existing `PT-ENRICH-LIMIT` (message gains "N MiB freed, M MiB still needed"). Orphan rows (no referencing pipeline row) are deleted by (a) only if `created` is older than the current publish call (a concurrent mid-publish set is written pipeline-last and must not be reaped).
- **Migration safety**: no schema change. Add meta key `retention_version='1'` (additive INSERT OR IGNORE into `enrichment_meta`; `extension_version` stays 1; v1 clients ignore the key and tolerate absent rows because every result is recomputable). Before the first retention that would delete rows in a database lacking a `project-pre-retention-*.sqlite3` backup, create one with the existing verified-backup routine (`_backup_before_create`, `storage.py:79`, generalized by a `label` argument). Deletion plus `retention_version` write are one transaction; failure rolls back and publish proceeds without GC (GC is best-effort except in the cap fallback). Space is returned to SQLite's free list, not the file; no automatic `VACUUM` (project may be large and locked); document `patchtrace cache`-style manual compaction as future work.
- **Pseudocode**
```
def apply_retention(self, current: Guard, protect: set[str]):
    if self.read_only: return 0
    pipes = [e for e in self.entries('pipeline')]            # newest first, integrity-checked
    live  = [p for p in pipes if not p.stale and p.guard == current]
    stale = [p for p in pipes if p not in live]
    keep  = live[:KEEP_CURRENT] + per_config(stale, KEEP_STALE)   # per_config groups by body.config_digest
    keep_ids = protect | refs(keep)                            # refs(): the 5 ids per pipeline body
    doomed = [id for id in all_ids_of_derived_kinds if id not in keep_ids and not orphan_too_new(id)]
    with self._db: DELETE ... WHERE id IN doomed ; INSERT OR IGNORE retention_version
```
Tests (new `tests/test_enrichment_retention.py`): 12 sequential edits then publish -> row count bounded and current generation intact (`load_default` still returns it); two profiles share one `wil` row and deleting one generation keeps it; cap fallback: fill to 120 MiB with stale rows, publish a 20 MiB generation succeeds; still-over-cap raises `PT-ENRICH-LIMIT` and leaves existing rows untouched; `secondary-matches` rows survive every path; read-only (future `extension_version`) store deletes nothing; backup created once, verified, not repeated; crash simulation (exception inside the transaction) leaves the table unchanged; v1 open/save/backup test with retention applied; orphan from a concurrent publish is not reaped.
Risk: deleting a generation a GUI still holds in memory (harmless: memory copy) ; mis-ref-counting shared `wil` rows (covered by test). 

## H2. History table bound , tier M (**needs owner decision**, see end)

Current: every `ProjectStore.save` inserts a full snapshot payload (`persistence.py:328`, `history` table `:253`), each up to 256 MiB, and nothing prunes it; the module docstring promises "append-only history" (`:1`). `history()` is read by tests and revision displays (`:359`).
Target default: keep the newest `HISTORY_KEEP = 100` rows **and** at most `HISTORY_MAX_BYTES = 512 MiB` of payload, never deleting the row whose `sha256` equals `current_snapshot.sha256`. Skip the INSERT when the new payload hash equals the newest history hash (idempotent re-save, e.g. the load-time "interrupted run" save). Prune runs in the same transaction after the INSERT (`DELETE FROM history WHERE sequence NOT IN (newest N) ...`), oldest first. First prune on an existing project creates the standard verified backup (`backups/project-pre-history-prune-*`). Revision numbers in snapshots are unchanged (they live in the payload, not the row).
Tests: 150 saves -> 100 rows, current row present, `history()` ascending by sequence; byte budget with large synthetic payloads; duplicate-hash save adds no row; pruning failure rolls back the save as a whole ("prior snapshot retained", `:333`); backup restore still reproduces `history()` for the retained rows (existing `test_core.py:78-84` pattern). Risk: loss of old audit trail (hence the decision flag); alternative with no loss is zlib-compressing rows older than 20 (schema change, rejected for this slice).

## H3. WIL status `partial` only for real partials , tier L/M

Current: `signals.detect` marks a one-sided pairing (added/removed function) with every detector `unavailable` and `SignalSet.status='unavailable'` (`signals.py:450-459, 907-919`). `pipeline.run` records the signals stage `complete` only if **all** sets are `complete` (`pipeline.py:210`), so any run containing one added or removed function reports stage `partial` and overall `partial` (`_overall`, `:154-165`). `_merge` then appends a `WIL` outcome carrying the **global** `wil_status` to every pairing (`:168-171, 240-244`), so a one-sided pairing has outcomes `{unavailable x7, complete}` and `ranking._evidence_status` returns `partial` instead of `unavailable` (`ranking.py:57-61`).
Target: status describes evidence quality of what was *requested and applicable*, not the presence of inapplicable pairings.
- Per pairing, the WIL outcome is derived per pairing: `unavailable` (reason from `wil.analyze` notes `one-sided-pairing` / `code-unavailable` / `pairing-ambiguous`) when WIL cannot apply, `partial` when notes contain `function-too-large` or `site-limit`, else `complete`; pipeline-level `wil_status` only overrides when the stage itself failed/cancelled.
- `SignalSet.status` ignores `unavailable` outcomes whose reason is a *category/one-sidedness* exclusion (an expected, structural not-applicable) when at least one other outcome is `complete`; it is `unavailable` only if all outcomes are not-applicable; `partial` only for truncation (`function-too-large`), `site-limit`, missing code on a required side of a 1:1 modified pair, or cancelled. Implement via a small `DetectorOutcome.reason` code enum is **not** added (contract frozen): use the existing `reason` text prefix constants `NOT-APPLICABLE:` vs `LIMIT:` defined in one module-level tuple and tested.
- Pipeline stage `signals` is `partial` only if some set has status `partial`; one-sided-only exclusions leave it `complete`. `ranking` per-entry `evidence` follows the same rule; a one-sided entry is `unavailable` (never silently "no defect").
Tests: run with one modified + one added + one removed pairing -> stage `complete`, overall `complete`, added/removed entries `evidence='unavailable'`, modified entry `complete`; truncated function -> `partial`; modified pair with null decompiled code on one side -> `partial`; WIL failed globally -> all `WIL` outcomes `failed`, overall `partial`; golden ranking arithmetic unchanged. Stage version bump for `ranking` (entry evidence changes). Risk: GUI/exports that print "partial" for one-sided rows change text (update `test_ui_enrichment.py`).

## H4. Contextual rerank requires binary evidence , tier M

Current: `contextual_rank` awards `identifier` points (+12, cap 24) from function-name tokens alone (`cve.py:416-429`); a pairing with **zero** signals and base score 0 can rise by 24 and, because `product` is only gated on "any contribution" (`:457`), by 28. SPEC-07 §8 says every contribution cites binary evidence and "no binary support -> 0". `binary_ref` today is `name:<fn>`, which is metadata, not change evidence.
Rule (normative): a pairing has **binary evidence** iff its `SignalSet` contains at least one `ChangeSignal` (any detector, including WIL, any confidence other than none) *or* a `qualifies=True` transition. Without it: `adjustment = 0`, `contributions = ()`, and `blocked` records `no-binary-evidence`. With it: `identifier` points stay +12/cap 24 but `binary_ref` becomes `signal:<lowest signal_id>` (and `detail` keeps the matched name); `cwe` unchanged (already requires moderate/strong aligned signal); `feature` unchanged (requires qualifying transition); `product` requires at least one *other* contribution (unchanged). One-sided or `unavailable` evidence never qualifies. Stage version bump `contextual` 1->2.
Test cases: (1) name token matches CVE, pairing has no signals -> adjustment 0 and order identical to base order; (2) same name, one weak ERR signal -> +12 with `binary_ref` starting `signal:`; (3) two matching tokens + two signals -> capped 24; (4) unavailable one-sided pairing with matching name -> 0; (5) matching name + product-module match, no signal -> 0 (product cannot lift alone); (6) CWE-787 + moderate BND -> +10 unchanged; (7) property: `context_score >= base_score` and `context_score == base_score` whenever no signals; (8) golden: existing contextual fixtures re-baselined, diff reviewed to show only no-signal pairings changed.

## H5. SIZE cast-only and BND added-loop false positives , tier M

SIZE current (`signals.py:755-784`): size args are compared as `_join(map(_norm_token, arg))` with **casts left in place**, so `memcpy(d,s,n)` -> `memcpy(d,s,(ulonglong)n)` (the decompiler re-emitting an implicit conversion) reports a size change. `_spilled_same` (`:787`) only forgives a single-temp spill.
Rule: define `size_canon(tokens)`: (1) `_strip_casts` repeatedly until fixpoint (type-only parentheses, incl. `*`); (2) remove redundant outermost `( ... )` pairs wrapping the whole argument; (3) numeric literals: strip integer suffix `[uUlL]{1,3}` and compare by integer value (`0x10`, `16`, `0x10U` equal); (4) apply `_norm_token`. SIZE fires iff canonical args differ **and** `_spilled_same` (using the same canonicalization on both sides) is false. A change of cast **type** alone (`(uint)n` -> `(ushort)n`) is not SIZE (it is INT's job; INT already handles width/sign casts on shared operands).
Counterexample fixtures (must **not** fire SIZE): `n`->`(ulonglong)n`; `(uint)n`->`(ulong)n`; `n`->`(n)`; `0x10`->`0x10U`; `16`->`0x10`; `(longlong)(int)n`->`n`; `malloc(n)`->`uVar1 = n; malloc(uVar1)` (existing). Must fire: `n`->`n - 1`; `n`->`(ulonglong)n - 1`; `n`->`m`; `sizeof(struct A)`->`sizeof(struct B)`; `0x10`->`0x20`.
BND current (`:526-533, 548-575`): `_added_cmps` yields any new comparison on a "control" line, and `control()` accepts `for`/`while` headers (`_CONTROL`, `:72, 301-309`). An entirely new loop `for (i = 0; i < n; i++) out[i] = in[i];` therefore reports "added bound comparison" although it is new structure, not a guard on pre-existing behaviour.
Rule: a comparison on a line whose first non-`}` token is `for` or `while` (loop header; `do { } while (c)` closer included) qualifies only if the edit's **old range** (`edit.old`) also contains a loop header of the same keyword, i.e. an existing loop's bound changed. A new loop header with no loop header in `edit.old` is skipped. `if`/`else if`/`&&`/`||` lines are unchanged. (Guards inside an added loop body still count.) Detector version bump BND 1->2.
Fixtures: must not fire: older has no loop, newer adds `for (i = 0; i < count; i++) { buf[i] = x; }`; newer adds `while (i < n) { p[i++] = 0; }`. Must fire: `for (i=0;i<n;i++) buf[i]=x;` -> `for (i=0;i<n && i<cap;i++) buf[i]=x;`; `while (i < n)` -> `while (i < min(n, cap))`; added `if (i >= cap) return -1;` before `buf[i]`. Risk: a real fix that rewrites a loop header together with its body might lose BND; accepted, other detectors (INT/OVF/VAL) and manual review remain.

## H9. Provider call cancellation latency (NVD/MSRC and LLM providers) , tier M

Current: `intelligence._attempt` opens the connection with a socket timeout of `min(10 s, remaining)` (`:298`) and reads with the same per-operation timeout; `cancel` is only polled between chunks (`:325`) and before each attempt (`:271`). A cancelled fetch can therefore block up to 10 s in `connect`/first byte and up to 10 s per stalled read. `providers.py:92` uses `TIMEOUT_SECONDS = 120` per socket operation with `cancel` polled between reads (`:95`), so cancelling an interpretation can wait up to 120 s.
Target: cancellation observed within 250 ms of `cancel.set()` for every blocking network call. Shared helper `interruptible(call, cancel, poll=0.1)` (new tiny module `netutil.py`, stdlib only): run `call` on a daemon thread, wait on a `threading.Event` in `poll` slices, on cancel return/raise `Cancelled` immediately, and have the abandoned thread close its response/socket when it eventually returns (flag set under a lock; no shared mutable result after abandonment). Apply to `opener(...)` and each `response.read(...)` in `intelligence._attempt` and the equivalent in `providers.py`. Per-operation socket timeouts stay as the upper bound for abandoned threads (bounded leak: at most one live thread per in-flight request; cap 4 abandoned threads, then new calls fail `PT-ENRICH-NETWORK` "previous requests still closing"). Tests use injected fakes with `threading.Event` blockers: fake opener blocks until released; assert `fetch` raises `PT-ENRICH-CANCEL` < 0.5 s after `cancel.set()`; blocked read same; no thread leak after release; deterministic clock tests remain (the helper takes `poll`/wait injection). Risk: abandoned thread holding the NVD key header (it already exists in memory; no new exposure) and Windows socket close races (native Windows CI covers `providers` loopback tests).

## H10. NVD pacing and HTTP 403 handling , tier M

Current: `fetch_all` issues requests back-to-back (`intelligence.py:230-245`) although the module docstring records NVD's public limit of 5 requests per rolling 30 s without a key, 50 with (`:12-13`); up to 64 CVEs x 2 providers are allowed (`MAX_CVES`). Retryable statuses are only 429/502/503/504 (`:46`); any other status, including NVD's rate-limit/forbidden **403**, becomes `PT-ENRICH-PROVIDER 'provider returned HTTP 403'` (`:317-318`) with no distinction between a rejected key and throttling and no back-off for following requests (test `test_enrichment_intelligence.py:142` expects the keyed 403 failure).
Target:
- Per-provider `Pacer(limit, window=30.0, clock, sleep, cancel)` (sliding window of request timestamps). Defaults: NVD keyless 4 per 30 s (one below the documented 5, safety margin), NVD with key 45 per 30 s, MSRC 1 per second. `acquire()` sleeps with the cancellable sleep until a slot is free; the sleep counts against a separate **plan deadline** (not the per-request 30 s `TOTAL_TIMEOUT`, which still starts at the actual send) = `ceil(n_requests / limit) * 30 s + 60 s`; exceeding it fails the remaining requests with a recoverable `PT-ENRICH-NETWORK 'pacing budget exhausted'` while keeping results already fetched. The consent preview (UI/CLI) states the minimum duration ("about 6 minutes for 40 NVD requests without a key").
- 403 policy: NVD **with** an API key -> `PT-ENRICH-PROVIDER` "NVD rejected the API key or access (HTTP 403)" , not retried, no further NVD requests in this plan (one error per remaining request, `skipped: key rejected`). NVD **without** a key -> treated as throttling: provider enters a cooldown of `max(Retry-After if valid, 30 s)`; the current request is not retried inside its 30 s window; it and any later NVD requests inside the cooldown are not sent and are reported as recoverable `PT-ENRICH-NETWORK 'NVD is rate limiting; retry after ~30 s or use an API key'`. MSRC 403 stays `PT-ENRICH-PROVIDER` (no cooldown). 429/503 `Retry-After` handling is unchanged; they also set the same cooldown so the pacer does not immediately resend.
Pseudocode: `acquire(): while len(window) >= limit or now < cooldown_until: sleep(min(needed, 1.0), cancel); check cancel; window.append(clock())`.
Tests (injected clock/sleep like the existing `Clock` fixture): 6 keyless NVD requests -> 5th waits until the first leaves the window and total sleep >= 30 s - epsilon, 0 sleeps with key for 10 requests; MSRC unaffected by NVD cooldown; 403 keyless -> remaining NVD skipped without opener calls, MSRC succeeds, result partial with named provider; 403 keyed -> key-rejected message, no key text in message; cancel during pacing sleep returns in < 0.5 s; plan deadline test; existing 403/429 tests updated deliberately (diff reviewed). Risk: NVD's actual enforcement is unverified live (recorded 2026-10-12 only from documentation); capture a live probe in `tests/fixtures/cve/README.md` as a separate non-gating step.

## H12. CVSS conflict only across providers , tier L

Current: `_conflicts` groups **all** CVSS records by version and flags a conflict when their `(base vector, score)` pairs differ (`cve.py:246-252`). `_parse_nvd` emits one record per NVD metric entry with `source='nvd:<metric source>'` (`:177-182`), so NVD's own Primary (NIST) and Secondary (CNA) entries for the same version, which routinely differ, produce a false "conflict" even when only NVD was queried. Severity conflicts have the same flaw (`:253-256`).
Target: provider = `source.split(':', 1)[0]`. For each CVSS version, build per-provider sets of `(base_vector, score)` ; a conflict exists only if at least two providers have records for that version **and** their sets are disjoint (no shared pair). Same rule for severity (providers with an empty severity are ignored, which today leaves NVD alone, so effectively no severity conflict from MSRC, documented). Multiple differing records inside one provider are kept in `cvss` unmodified (information preserved) and add no conflict. Conflict text stays `cvss <version>: nvd=..; msrc=..` using provider names. `snapshot_id` unaffected (digests of responses); `conflicts` is derived, so existing stored snapshots keep their old strings until re-normalized: loaded snapshots are not re-derived (document).
Tests: NVD-only with Primary 9.8 / Secondary 8.1 same version -> no conflict; NVD 9.8 vs MSRC 7.5 same version -> conflict; NVD primary and secondary where MSRC equals the secondary -> no conflict (shared pair); versions 3.1 vs 4.0 never compared; MSRC temporal metrics ignored by `_base_vector` (unchanged).

## H13. `select_latest` provider loss , tier M

## Phase D track B amendments (2026-10-14; normative, supersede the H1/H2 backup sentences above where they differ)
- **Verified pre-prune backup (H2, applies to H1 too).** No prune deletes a row (history prune, enrichment retention, `make_room`, engine-run pruning) unless a trusted backup exists. Module `verified_backup.py` (stdlib + `ingestion.safe_path`, no Qt): a new backup is written with the SQLite backup API to `backups/project-pre-<label>-<UTC stamp>.sqlite3.part`, the writing connection is closed, the file is **re-opened read-only** and must pass `PRAGMA integrity_check` and return the same answers as the live database to identity queries (current snapshot hash; plus `COUNT(*), MAX(sequence)` of `history` or `COUNT(*)` of `enrichment_entries`); only then is it renamed to the final name. An existing backup is trusted only if it re-opens read-only, passes `PRAGMA quick_check`, holds the live project id and the label's table; the verdict is cached per process by (path, size, mtime_ns), so a backup is re-checked once per process and whenever its file changes, not on every save. Labels: `history-prune` (H2), `retention` (H1), `enrichment` (pre-extension, additionally requires the live snapshot hash). Failure is never data loss: the prune is skipped and every row kept (history: the save itself still commits, a warning is logged and the session does not retry the copy; retention: `apply_retention`/`prune_runs` return 0; `make_room` raises recoverable `PT-ENRICH-LIMIT` "retention backup failed"). History: the first prune of a session that lacks a trusted backup is deferred to a second transaction right after the save commits (the copy cannot run inside the save transaction); later prunes of that session stay inside the save transaction. One backup per label is kept and reused ("taken once"); it holds every row deleted by the first prune, not rows created after it (decision 1 above: bounded history is accepted).
- **Legacy duplicate raw cleanup on open (H8).** `ProjectService.open(root, *, maintenance=True)` runs `raw_cleanup.cleanup_legacy_raw_duplicates` after a successful load (never inside `_verify_files`; read-only series readers pass `maintenance=False`). Scope, closed: for each run of the loaded snapshot whose `raw_path` is exactly the legacy copy `runs/<id>/raw/result.ghidriff.json`, the candidates are regular files (no links/junctions) matching `runs/<id>/raw/json/*.ghidriff.json`. A candidate is removed only if the kept `raw_path` file still hashes to `raw_sha256` and the candidate has the same size and SHA-256; anything else (different bytes, unreadable, link, other names, `artifacts/`, quarantine or unreferenced run directories) is left and logged. Backed up and reversible: before each removal one JSON line `{"v":1,"run_id","removed","kept","sha256","size","utc"}` is appended (flushed and fsynced) to `backups/raw-duplicates.jsonl`; the bytes stay recoverable from the verified kept copy, and `raw_cleanup.restore_raw_duplicates(root)` recreates every journalled file whose path is absent after re-checking the kept copy's hash. Idempotent: a second open finds nothing. Best effort: it never raises and never blocks the open; directories are not removed.
- **H3 truncation gap.** A truncated function (`function-too-large`) is `partial` for every applicable detector even when the scanned part holds no non-noise edit (the change may sit in the unscanned tail); before, such a pairing reported `complete` with "no non-noise changed hunk". Untruncated pairings are unchanged. The per-pairing WIL outcome follows the same rule: a truncated function on either side makes it `partial` (`LIMIT: function-too-large`) even when no transition was found in the scanned part. No contract change; covered by the `signals` stage version already bumped in this release cycle plus the algorithm digest below.
- **SPEC-07 §4 `validate_location` (P1 "spec validate_location").** `views.validate_location(project_or_run_view, loc) -> FunctionView` is the single check: the function exists in the run's pairings, belongs to `loc.run_id`, `loc.artifact_id` and `loc.side` (`PT-ENRICH-OWNERSHIP` otherwise), and the 1-based lines exist and hash to `loc.excerpt_sha256` (`PT-ENRICH-STALE` otherwise). The derived-cache hit path (`pipeline._locations_owned`) uses it. GUI navigation (`ui.py`, not in this track) still checks only the function id: wiring it there is left to the UI owner.
- **Algorithm digests in derived-cache keys and stored rows (P2 "derived-cache keys lack algorithm digest").** `identity.constants_digest(domain, version, namespaces, exclude)` digests every plain-data module constant (int/str/bool/None, compiled regex as `{re, flags}`, float as its repr, tuples/lists, sets as sorted lists, dicts with stringified keys, dataclass instances without callable fields; functions, classes, modules and dunder names are skipped). `pipeline.algorithm_digests()` returns one digest per stage: `signals` (constants of `signals`, `views`, `alignment`; `CANCEL_EVERY` excluded), `wil` (`wil` + the `signals` set, because WIL reuses its normalization), `ranking` (`ranking`), `contextual` (`cve`). Each stage id adds the input `'algorithm': <digest>` (stage versions unchanged), so the derived cache misses and new rows get new ids whenever an algorithm constant changes, even if nobody bumps a version. The `pipeline` row body gains the additive key `algorithms` (stage -> digest); `load_default`/`load_profile` serve a row only when its stage versions **and** `algorithms` equal the running code's, otherwise the note reads "Stored ranking is stale (computed by an older PatchTrace version). Rank changes again." Rows written before this change have no `algorithms` and are recomputed once (deliberate re-baseline, listed in `docs/qa.md`). Logic changes that touch no constant still need a stage/detector version bump; a golden-digest test makes every constant change a visible, reviewed re-baseline and checks that the digests are identical on Linux and Windows.
- **H10 live probe (separate, non-gating).** `tools/live_nvd_probe.py` checks direct TCP reachability of each provider host (no proxy, like the transport), then runs the real `patchtrace correlate --fetch` (keyless; two CVEs by default so the 6 s NVD pacing is observable) on a synthetic sample project and writes `build/live-status/cve-providers.json` (`passed | failed | blocked`, per-provider detail, consent preview, pacing evidence). Unreachable hosts, `PT-ENRICH-NETWORK`/rate limits and probe timeouts are `blocked`; normalization failures, CLI errors and broken pacing are `failed` (exit 1). `.github/workflows/live-nvd.yml` runs it weekly and on demand only; it is never a required check and its results are never summed with pytest counts.
- **Performance (no contract change).** Diff hunks are derived lazily, canonical JSON has an exact-type fast path, `_clean` skips delimiter-free lines, WIL skips functions without `Feature` text and reuses B1's hunk filter, and `pipeline.run` pauses the cyclic GC (re-entrant, restores the caller's setting). The 500 ms derived-cache objective at 10,000 pairs remains unmet: strict re-validation of the cached records and ownership revalidation are kept by design; numbers in `docs/qa.md` `[B:hardening]`.
